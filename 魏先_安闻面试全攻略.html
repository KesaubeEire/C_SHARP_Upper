Q1. 上位机多 PLC 数据采集架构是怎样的？采集时 UI 卡顿怎么解决？ P0 必问 项目一
→ 你可以这样回答（结合项目一）：

"我在七轴分选监控系统里对接了 3 台 PLC——1511T 用 Profinet、1215C 和 200 SMART 走 Modbus TCP。架构上我做了三层：

① 协议层：每台 PLC 独立一个通信实例，各自维护连接状态和重连逻辑，互不影响。

② 采集调度层：用 Task.Run + async/await 异步采集，3 台 PLC 并行轮询，刷新周期控制在 200ms 以内。关键设计是生产者-消费者模式——采集线程只管往 Channel<T> 里写数据，UI 线程通过 await foreach 消费数据并更新界面，两边解耦，采集慢不会拖 UI。

③ 显示层：UI 更新用 Control.Invoke（WinForms）封送到主线程，或者 async/await 自动捕获 SynchronizationContext 回到 UI 线程。实时曲线用 GDI+ 自绘，只重绘变化区域不做全屏刷新。

核心思路就是'采集不卡 UI，UI 不拖采集'——异步采集 + 有界缓冲区 + 批量 UI 更新。"

面试官可能会追问："Channel<T> 有界容量满了怎么办？" → 答："背压机制，WriteAsync 会自动等待，不会丢数据也不会爆内存。"
Q5. async/await 和 Task.Wait() 有什么区别？为什么上位机不能用 Wait()？ P0 必问
→ 你可以这样回答：

"Task.Wait() 是同步阻塞当前线程，会卡死 UI——WinForms 的消息泵被堵住，界面直接白屏未响应。

async/await 则是'异步不阻塞'——遇到 await 时当前方法挂起，线程回线程池去处理别的事，等异步操作完成后再调度回来继续执行。

上位机为什么必须用 async/await：串口读数据或者 PLC 轮询，一次通信可能要 50-200ms。如果每秒轮询 5 次还用 Wait()，UI 线程全部时间都被占满，用户点什么都没反应。用 async/await 的话，等待期间线程可以处理用户点击、刷新其他控件。

还有一个坑：Wait() 在 UI 线程上可能死锁——因为 await 默认要回到原始 SynchronizationContext（UI 线程），但 UI 线程被 Wait() 堵住了回不来，就死锁了。用 ConfigureAwait(false) 可以避开，但根本方案还是别用 Wait()。"

Q11. C# 实现 Modbus 通信你用过什么库？为什么选择它？ P0 必问
→ 你可以这样回答：

"我既用过现成的库，也自己写过通信库：

① 自己封装 Modbus 协议类：学习阶段为了搞懂底层原理，手写了帧组装（功能码 + 地址 + 数据 + CRC 计算）和响应解析。CRC-16 查表法比逐位计算快 8 倍，适合高频轮询。这个经历让我面试时能讲清楚每个字节的含义。

Q14. 设备突然断线，上位机怎么处理？断线重连机制怎么设计？ P0 必问 项目一+二+三
→ 你可以这样回答：

"断线处理我分四层来搞：

  1. 检测层 —— 怎么知道断了？
    • Modbus 发送后超时没收到响应（通常设 500ms~1s timeout）
    • 串口 SerialPort.ErrorReceived 事件捕获硬件异常
    • 连续 3 次超时才判定断线（防偶发干扰误判）
  2. 重连层 —— 怎么恢复？
    • 指数退避策略：1s → 2s → 4s → 8s → 上限 30s，避免疯狂重连
    • 每次重连前先 Close() 再 Open()，确保串口/连接状态干净
    • 重连成功后自动补读断线期间的配置/状态寄存器
  3. 数据层 —— 断线期间数据怎么办？
    • 采集数据标为 '离线'，时间戳精确标记断线时段
    • 关键工艺参数先用 SQLite 本地缓存，恢复后补传 MES
  4. UI 层 —— 怎么告诉操作员？
    • 设备状态灯变红（绿=在线 / 黄=重连中 / 红=离线）
    • 弹窗报警 + 记录报警历史到数据库
    • 如果 30s 还没恢复，声光报警（现场蜂鸣器）

这个设计在我三个项目里都用了，只是重连参数根据设备重要性微调。"

Q6. 程序崩溃或突然断电，怎么保证采集数据不丢？ P0 必问 项目一+三
→ 你可以这样回答：

"分三层保障：

① 即时写盘：不是攒一批再写，而是每条数据到达就 INSERT（SQLite WAL 模式下写入很快）。或至少每 100 条/每 5 秒批量 flush 一次。

② 双存储兜底：本地 SQLite（毫秒级写入 + WAL 模式崩溃恢复）做第一道防线，关键数据异步同步到 SQL Server/MES。即使 SQL Server 网络断了也不丢数据——SQLite 在本地一直记着。

③ 异常捕获 + 未处理异常：try-catch 包住采集循环体，单个设备的异常不影响其他设备。AppDomain 级别挂 UnhandledException 做最后一道兜底，记录崩溃时间点后再退出。

④ .NET 6+ 可以用 IHostApplicationLifetime 的 ApplicationStopping token，在程序被 kill 时做最后 flush。WinForms 里重写 OnFormClosing 也能做同样的事。"

Q12. 大小端问题 —— 上位机怎么处理 Modbus 数据中的字节序？ P0 必问
→ 你可以这样回答：

"Modbus 默认是大端序（Big-Endian）——高字节在前。但 PC（x86）是小端序，所以读回来必须转换。

坑：不同 PLC 厂商对 32 位寄存器的字节序还不一样：
· 西门子：两个字（Word）顺序是小端，如 0xABCD EFGH → 低字在前 ABCD，高字在后 EFGH
· 三菱/施耐德：高字在前
· 有些国产 PLC 字节序更乱，4 字节随便排列

我的处理方式：在 ModbusProtocol 类里封装一个通用转换，用 BitConverter + Array.Reverse。还可以用 BinaryPrimitives.ReadInt32BigEndian()（.NET 6+），一行搞定不用记位运算。

最佳实践是把字节序做成配置项——PLC 型号映射到一个 Endianness 枚举（ABCD / CDAB / BADC / DCBA），换 PLC 只改配置不重编译。"

S6. Modbus RTU 帧格式长什么样？CRC 校验怎么算的？ P0 必问
→ 你可以这样回答：

"RTU 帧结构：地址码(1B) + 功能码(1B) + 数据区(NB) + CRC校验(2B)

比如读 1 号站保持寄存器 40001，长度 1 个字的请求帧：

01 03 00 00 00 01 84 0A
│  │  └─────┘ └──┘ └───┘
│  │   起始地址  数量  CRC-16
│  └─ 功能码 03=读保持寄存器
└─ 站号 1

CRC-16 算法：生成多项式 0xA001，初始值 0xFFFF。每个字节与 CRC 低 8 位异或，然后右移 8 次——移出的位如果是 1 就异或多项式。实际项目用查表法——预计算 256 个字节的 CRC 值放入数组，查表代替逐位计算，效率提高 8 倍。

TCP 就没有 CRC 了——因为 TCP 层已经保证了数据完整性，用 MBAP 头（7 字节）替代了地址码和 CRC 的位置。"

S7. TCP 粘包/半包是什么？Modbus TCP 怎么解决？ P0 必问
→ 你可以这样回答：

"TCP 是流协议，没有消息边界——你发了两帧数据，接收方可能一次收到（粘包），也可能分三次收到（半包）。

Modbus TCP 的解决方案就是 MBAP 头——7 字节固定头，其中第 5-6 字节是长度字段，告诉接收方'这条消息后面还有多少字节'。程序读到 MBAP 头 → 解析长度 → 按长度精确接收剩余数据，天然不粘不半。

对比 Modbus RTU，它没有长度字段，只能靠3.5 字符的时间间隔来判断帧结束——如果发送太快两帧之间间隔不够，就会粘包。所以 RTU 轮询时要留帧间间隔，不然 485 总线上可能丢数据。"

S1. IDisposable / using —— 为什么串口连接要用 using？ P0 必问
→ 你可以这样回答：

"using 是 try-finally 的语法糖——无论正常执行还是抛异常，finally 块里都会调 Dispose()，保证资源释放。

串口为什么必须 Dispose：SerialPort 占用了 Windows 内核的串口句柄。不释放的话：① 串口一直被占用，别的程序打不开；② 进程退出后 OS 会回收，但进程运行期间就是资源泄漏；③ 硬件串口数量有限（通常 1-8 个），泄漏一次少一个。

上位机的典型用法：

// ✅ using 语句 —— 作用域结束自动 Dispose
using (var sp = new SerialPort("COM1", 9600))
{
    sp.Open();
    // ... 读写操作
}  // 这里即使抛异常也会关串口

// ✅ C# 8+ using 声明 —— 更简洁
using var conn = new SqlConnection(connStr);
// ... 方法结束时自动 Dispose

我的 DatabaseManager 就实现了 IDisposable——在 Dispose 里 Close + Dispose 连接对象。用它的地方只要 using var db = DatabaseManager.CreateSQLite(...) 就行。

进阶：C# 8 还有 IAsyncDisposable——串口关闭可以异步做：await using var sp = ...。"

S2. 装箱拆箱是什么？上位机里怎么避免？ P0 必问
→ 你可以这样回答：

"装箱：值类型（int, struct, double）→ 转成 object，会在堆上分配一个新对象，把值 copy 过去。有 CPU 和内存开销。

拆箱：object → 转回值类型，从堆上取出值 copy 回栈上。

上位机里典型坑：Modbus 数据解析时，如果用了 ArrayList（存 object），每个寄存器值都要装箱。1000 个寄存器轮询一次就 1000 次装箱。

解决方案就是泛型集合：List<int> / List<ushort>。泛型在编译时就确定了类型，不存在 object 中转，零装箱。Dictionary<int, PlcDataPoint> 也一样，按设备地址索引数据结构不需要拆箱。

面试可以补充一句：.NET 的 Span<T> 更进一步——连堆分配都省了，直接在栈上操作内存切片，Modbus 帧解析性能能再提一个量级。不过这是加分项。"

S10. 上位机怎么和 MES 系统对接？数据上报怎么做？ P0 必问 项目一+三
→ 你可以这样回答：

"MES 对接本质就是把产线数据报给上层系统。几种方式：

① REST API 上报（常用的）：上位机把产量、合格率、设备状态打包成 JSON，POST 到 MES 的 HTTP 接口。C# 用 HttpClient + async/await，非阻塞上报，不影响采集。

② MQTT 推送：适合实时性要求高的场景（设备报警、关键工艺参数变化）。用 MQTTnet 库，发布到 MQTT Broker，MES 订阅。西门子 PLC 还可以直接通过 MQTT 模块上云。

③ 数据库直连：上位机写 SQL Server 表，MES 定时读。简单粗暴但耦合度高。

④ 文件交换：导出 Excel/CSV，MES 定时导进。最原始但兼容性最好。

我的项目里的实践：七轴系统中关键工艺数据（分选结果、入库记录）通过 POST 上报到工厂 MES。中间加了一层本地 SQLite 作为缓冲——网络断的时候先存本地，恢复后补传。上报格式是 JSON，带时间戳 + 设备编号 + 工位编号 + 批次号，方便 MES 端做追溯。"

"上位机最常用的是 RS485——工业现场距离远、干扰大、一主多从（多台 PLC/变频器挂在同一条总线上）。Modbus RTU 就是跑在 RS485 上的。

现场调试经验：终端电阻一定要接（120Ω 并在 A/B 两端），不接的话信号反射会导致通信时断时续。波特率越高距离越短，9600 跑 1200 米没问题，115200 最多 100 米左右。"

Q3. 委托和事件的区别？上位机里怎么用？ P0 必问
→ 你可以这样回答：

"核心区别：事件是委托的封装，限制了外部只能 += / -=，不能直接 Invoke 或赋值覆盖。

// delegate —— 外部可以直接 Invoke，甚至可以 = null 清空
public Action<string> OnDataReceived;  // ❌ 外部可以 OnDataReceived = null

// event —— 外部只能订阅/取消，触发权在类内部
public event Action<string> OnDataReceived;  // ✅ 安全封装

上位机应用：

  • 串口收到数据 → 触发 OnDataReceived 事件，通知 UI 层更新
  • PLC 断线 → 触发 OnConnectionLost 事件，报警模块订阅它
  • 配方切换 → 触发 OnRecipeChanged 事件，多个模块各自处理

最经典的委托应用是跨线程更新 UI：this.Invoke(new Action(() => label.Text = "xxx"))——把一个 Action 委托封送到 UI 线程执行。这行代码在三个项目里到处都是。"

Q2. 你做过什么 C# 上位机项目？遇到什么坑？怎么解决的？ P1 常问 全部项目
→ 你可以这样回答（选项目一+二，有对比有亮点）：

Q16. 梯形图(LAD)/结构化文本(ST)/顺序功能图(SFC) 各用在什么场景？ P1 常问
→ 你可以这样回答：

"三种语言各自有擅长的场景：

S8. PLC 扫描周期是什么？上位机通信怎么配合？ P1 常问
→ 你可以这样回答：

"PLC 不是并发执行的，它是一个循环扫描的机器：读输入 → 执行程序 → 写输出 → 通信处理 → 回来读输入，这样一个循环叫一个扫描周期。小型 PLC 一般几毫秒到几十毫秒。

上位机通信的关键：PLC 只在扫描周期的通信处理阶段才响应 Modbus 请求。如果上位机轮询太快（比如 10ms 一次），而 PLC 扫描周期是 20ms，那有些请求会排队等待，表现为通信时断时续。

所以上位机轮询间隔要 > PLC 扫描周期的 2-3 倍——比如 PLC 扫描 20ms，上位机 50-100ms 轮一次就够了。这在我的项目里做过调优——初始用 20ms 轮询，发现丢帧率高，调大到 80ms 后就稳定了。

还有一个坑：通信处理在扫描周期里的占比不是 100%，西门子 S7-200 通信只占扫描周期的 10-20%。所以实际有效通信带宽远小于理论值。"

Q17. 伺服电机控制 —— 脉冲方向 vs EtherCAT 总线？ P1 常问 项目一+三
→ 你可以这样回答：

"脉冲方向（Pulse + Direction）：传统方式，PLC 发脉冲序列给伺服驱动器，频率控制速度、数量控制位置。简单可靠，但接线多（一轴至少 2 根信号线 + 使能 + 报警），适合≤4 轴的小系统。

EtherCAT / Profinet 总线：一根网线搞定所有轴，实时性强（μs 级同步），适合多轴联动（>4 轴）。数据交换不只是位置/速度，还能读伺服内部状态（温度、负载率、故障码）。

我的项目：项目三用了 V90 伺服通过 Profinet 连 S7-1200，走的就是总线方式——上位机通过 PLC 中转读伺服的位置/速度/转矩数据。上位机不直接跟伺服通信（安全考虑——控制权在 PLC，上位机只监控+调参）。

脉冲方向我也在培训中实操过——用 S7-200 SMART 的高速脉冲输出控制步进电机。核心是加减速曲线（梯形/S 形），避免突然启停丢步。"

Q18. 变频器在产线中应用？上位机怎么监控变频器？ P1 常问 项目一+三
→ 你可以这样回答：

"变频器就是控制交流电机转速的设备——在产线上驱动传送带、风机、水泵、压缩机等。

上位机监控的核心参数：运行频率(Hz)、输出电流(A)、输出电压(V)、故障代码、运行状态（运行/停止/故障）。

我的项目实践（项目三）：V20 变频器通过 Modbus RTU 和上位机通信。用 03 功能码定时读取频率和电流画实时曲线，06 功能码远程设定频率值。关键设计是频率写入加了范围限制（最低 5Hz 最高 50Hz），防止误操作——比如输了个 999 进去马达飞车。

项目一用的是 G120——它带 Profinet 接口，数据走 Profinet 到 1511T PLC，上位机再从 PLC 读，不直接跟变频器通信。这是工业常见做法——PLC 做控制层，上位机做监控层，物理隔离提高安全性。

故障代码一定要存下来——变频器报故障时第一时间抓取故障码，方便事后追溯原因（过流/过压/过热/缺相）。"

Q13. 上位机怎么和变频器/伺服通信？ P1 常问 项目一+三
→ 你可以这样回答：

"两种方式我都用过：

① 上位机直连设备（项目三 V20 变频器）：通过 Modbus RTU/RS485，上位机做主站直接读变频器寄存器。好处是架构简单，不依赖 PLC。坏处是控制权分散，安全性差——上位机和 PLC 都可能改参数，容易冲突。

② 上位机通过 PLC 中转（项目一 G120+V90）：变频器/伺服连到 PLC（Profinet/脉冲），PLC 负责实时控制，上位机只做监控和数据采集。这是工业标准做法——PLC 做硬实时闭环，上位机做软实时监控，职责清晰、安全。

变频器寄存器要查手册：不同品牌的寄存器地址不同。西门子 G120 的通讯手册里频率给定是 40100、状态字是 40110——这些地址必须对着手册一个个配，配错了读回来就是乱数。

还有一个安全点：写频率/启停命令一定要加确认——我的界面上频率调节有个'应用'按钮，确认后才写入。防止操作员手滑直接把传送带速度从 50Hz 改成 5Hz。"

Q4. 泛型在上位机里有什么用？ P1 常问
→ 你可以这样回答：

"最大的好处：类型安全 + 避免装箱拆箱。举例：

// ❌ 不用泛型 —— ArrayList 存 object，装箱 + 类型不安全
ArrayList points = new ArrayList();
points.Add(new PlcDataPoint());  // 装箱
var p = (PlcDataPoint)points[0]; // 拆箱，类型转换可能抛异常

// ✅ 泛型集合 —— 编译时类型检查，零装箱
List<PlcDataPoint> points = new List<PlcDataPoint>();
points.Add(new PlcDataPoint());  // 不装箱
var p = points[0];               // 不拆箱，类型安全

实际项目里的典型应用：

  • Dictionary<int, PlcDevice> —— 按设备 ID 索引设备对象
  • List<AlarmRecord> —— 报警列表，直接绑定 DataGridView
  • 泛型 Repository：IRepository<T> 接口，CRUD 操作复用
  • 泛型方法：ModbusValue ConvertEndian<T>(byte[] data) 统一处理不同数据类型的字节序转换

上位机数据量大（每秒可能数百条寄存器值），装箱开销累积起来很可观。泛型是基础素养。"

Q10. CAN 总线是什么？用在什么场景？ P1 常问
→ 你可以这样回答：

"CAN 是车载/工业设备的主流总线协议。核心特点：多主架构——任意节点都能主动发数据，不像 Modbus 只能主站轮询；优先级仲裁——ID 越小的帧越优先；差分信号——抗干扰强。

车载冰箱场景：冰箱控制模块通过 CAN 和整车 ECU 通信——上报温度、故障状态，接收整车指令（比如停车后延时断电）。

上位机的角色：产线 EOL 测试时，上位机可能需要通过 USB-CAN 模块监听 CAN 总线，验证冰箱和模拟 ECU 之间的通信是否正确。C# 可以用 PCAN-Basic API 或 SocketCAN 来收发包。

坦诚说我的项目里 Modbus 和 Profinet 用的多，CAN 只在课程里学过基础帧格式和 CANopen 概念。但协议本质都是 '帧结构 + 校验 + 地址'——上手思路一样。

Q7. 上位机用什么图表库画曲线？ P1 常问
→ 你可以这样回答：

"分三层：

① 自己用 GDI+ 画：曲线简单时没必要引第三方库。在 PictureBox.Paint 事件里用 Graphics.DrawLine 连点成线。关键是双缓冲——先画到内存 Bitmap 再一次性贴到屏幕，不闪烁。我在项目二里用这种方式画了 6 工位的状态动画。

S4. Span<T> / Memory<T> 在协议解析中怎么用？ P1 常问
→ 你可以这样回答：

"Span<T> 是栈上的内存切片，零堆分配，适合高性能字节处理。

Modbus 帧解析场景：

// 传统：每次解析都创建新数组，GC 压力大
byte[] frame = ReadModbusFrame();  // 堆分配
byte[] data = frame[3..^2];        // 又分配一个数组

// Span<T>：切片指原缓冲区，零分配
Span<byte> frame = ReadModbusFrame();
Span<byte> data = frame.Slice(3, frame.Length - 5);  // 不是新数组，只是指针

上位机收益：每秒解析数百帧 Modbus 报文，省掉大量 byte[] 分配和 GC 回收，CPU 占用率能降 30-40%。

Memory<T> 是 Span 的堆版本——async 方法里不能传 Span（ref struct 有栈限制），用 Memory<T> 代替。

坦诚说这是 .NET Core 2.1+ 的新特性，我课程学的 .NET Framework 4.8 项目没用过。但在 .NET 10 项目中我会优先用——API 很直观。"

S3. record vs class 有什么区别？上位机里怎么选？ P1 常问
→ 你可以这样回答：

"record 是 C# 9 引入的值语义引用类型——核心是 不可变性 + 值相等。

维度classrecord
相等性引用相等（同一个对象）值相等（属性一样就相等）
可变性默认可变默认不可变（init 属性）
语法传统简洁：record Point(int X, int Y);
With 表达式不支持p with { X = 10 } 快速拷贝

上位机推荐用法：
· Modbus 寄存器、配方参数、报警记录 → record（数据载体，不改）
· 串口连接、UI 控件、业务逻辑 → class（有状态，会变）

一行 record PlcDataPoint(int Address, float Value, string Unit); 顶 class 的构造函数 + Equals + GetHashCode 一堆代码。但 .NET Framwork 4.8 不支持，我现在用 .NET 10 项目会用。"

Q29. 和设备供应商（PLC/伺服/相机）怎么配合？ P1 常问
→ 你可以这样回答：

"和设备供应商打交道，关键三样东西：通讯手册、寄存器表、调试工具。

① 前期：明确接口文档——供应商交付时必须提供寄存器地址表、通信协议规格、故障码定义。在项目启动阶段就要到这些资料，否则开发做一半发现地址不对，工期全耽误。

② 过程：分阶段联调——先在供应商办公室做通信连通性测试（ping 通 + 读几个已知寄存器验证），再去现场联调全流程。避免到现场了才发现通信有问题。

③ 碰到问题：用调试工具定位——Modbus Poll 手动发包验证设备是否正常响应；Wireshark 抓包看帧格式对不对。先排除自己代码的问题，再把抓到的异常帧发给供应商。

④ 经验：供应商文档经常有错——寄存器地址偏差一位（比如应该是 40100 实际是 40099）、字节序标反了等等。第一件事不是改自己代码，而是用调试工具确认实际行为。"

Q22. 压缩机式 vs 半导体式车载冰箱 有什么区别？ P2 加分
→ 你可以这样回答：

"核心区别是制冷原理不同：

压缩机式（主流，安闻方向）：和家用冰箱一样，压缩机制冷剂循环（压缩→冷凝→膨胀→蒸发）。优点：制冷效率高（可达 -20°C），适合大容积。缺点：体积大、有轻微噪音振动。产线检测重点：制冷速率、最低温度、功耗、噪音。

半导体式（无压缩机）：靠帕尔贴效应——电流通过半导体制冷片，一面冷一面热（风扇散热）。优点：体积小、无振动、可加热（反接）。缺点：制冷效率低、环境温度高时效果差、一般只能比环境低 15-20°C。适合小容积保温杯型冰箱。

上位机测试区别：压缩机式要测高压/低压、压缩机电参数；半导体式测制冷片功耗和热端温度。测试参数不一样但测试流程类似——都是给电→等稳定→测性能曲线→判 PASS/FAIL。"

Q25. 车载冰箱产线检测标准有哪些？ P2 加分
→ 你可以这样回答：

"主要看 QC/T 1196-2023《汽车用电动压缩机车载冰箱》行业标准。核心检测项：

  • 制冷性能：在环境温度 32°C、43°C 下的降温曲线和最低温度
  • 绝缘电阻：电气安全 —— DC 500V 测试，绝缘电阻 ≥ 1MΩ
  • 耐电压：AC 500V 1 分钟，无击穿闪络
  • 噪声：距冰箱 1m 处 ≤ 45dB(A)（压缩机式）
  • 功耗：额定电压下运行功率在标称值 ±10% 内
  • 密封性：门封条密封性测试（防止冷气泄漏）
  • 振动耐久：模拟车辆颠簸，运行状态下随机振动测试

上位机要做的是把每个检测项的实测值、标准值、判定结果完整记录下来，生成出厂检验报告（PDF/Excel）。关键是不可篡改——谁测的、什么时候测的、结果是什么，全链路可追溯。

（如果追问：这是汽车行业 QC/T 标准，类似电器行业的 GB 标准。具体数值可能记不准，但测试项的大类我理解。）"

Q26. IATF16949 / APQP / PPAP 是什么？ P2 加分
→ 你可以这样回答：

"汽车行业质量管理的三个核心概念：

IATF16949：汽车行业质量管理体系标准，高于 ISO9001。核心思想是缺陷预防 + 持续改进 + 减少变差。对产线的影响：生产过程必须有完整的追溯记录——这台冰箱用的哪个供应商的压缩机、哪个批次的发泡料、在哪个工位测的什么参数。这些都是上位机的数据要记录的。

APQP（先期产品质量策划）：产品开发时就要把质量控制想好。分 5 个阶段——策划→设计→过程设计→验证→量产。上位机开发在"过程设计"阶段介入——定义需要采集哪些过程参数、检测哪些指标、数据怎么存储。

PPAP（生产件批准程序）：量产前给客户提交 18 项文件证明你的产线能稳定产出合格品。其中包含初始过程能力研究（CPK ≥ 1.33）。上位机产出的测试数据就是 PPAP 报告的数据来源。

Q27. IQ/OQ/PQ 设备验证是什么？ P2 加分
→ 你可以这样回答：

"设备安装调试的三阶段验证：

IQ（安装验证）：设备/系统按规格安装了吗？——检查硬件型号、软件版本、通讯接线、电气安装是否符合设计文档。

OQ（运行验证）：设备能按预期运行吗？——用已知标准件/标准信号测试，验证上位机采集精度、报警触发、数据记录功能。比如输入标准 4-20mA 信号，验证上位机显示值误差在 ±0.5% 内。

PQ（性能验证）：在实际生产条件下能持续稳定产出合格品吗？——连续跑一批产品（通常 3 批），验证 CPK ≥ 1.33、不良率在目标以内、上位机数据完整性和追溯性。

上位机的角色：OQ 阶段验证采集精度、通信稳定性；PQ 阶段提供连续运行的生产数据和检验报告。每一步都有签字确认——IQ/OQ/PQ 完成才能放行量产。

这本质上就是我的项目里 'IO 对点 → 单机调试 → 联机联调 → 试运行' 的正式化版本，只不过汽车行业多了签字和文件管控。"

Q21. 产线节拍分析和 OEE 提升 P2 加分
→ 你可以这样回答：

"OEE = 可用率 × 性能率 × 质量率

· 可用率 = 实际运行时间 / 计划生产时间（排除故障、换型、缺料等停机）
· 性能率 = 实际产量 / 理论产量（排除速度降低、微小停顿）
· 质量率 = 合格品 / 总产量

上位机能做什么：精确记录每次停机的原因和时长（报警系统自动记录），计算每个工位的节拍时间（传感器信号时间戳差值），统计产量和合格率。有了数据才能知道哪里是瓶颈——是某个工位节拍太慢？还是某台设备故障率太高？

提升思路（举例）：假设 EOL 测试是瓶颈——测试一台冰箱要 5 分钟。上位机能做的是：① 优化测试流程，去掉不必要的等待时间；② 并行测试多工位，增加产能；③ 数据分析找到测试失败最多的是哪个参数，反馈给工艺改善。这些数据就是 OEE 分析的基础。"

S9. 产线安全系统 —— 急停/安全门/光栅怎么集成到上位机？ P2 加分
→ 你可以这样回答：

"安全系统最重要的原则：急停必须硬接线，不能走软件。拍下急停按钮直接切断动力电源，不经过 PLC/上位机任何处理——这是安全法规要求。

上位机的角色是监控，不是控制：
· 急停状态 —— 采集急停继电器的辅助触点信号，显示在界面上（哪个区域急停了）
· 安全门/光栅 —— 通过安全 PLC（如西门子 F-CPU）的安全输入模块采集，上位机只读不写
· 报警记录 —— 安全事件触发时自动记录时间、位置、状态，永久存储不可删除

上位机绝对不能做的事：用软件复位急停。急停必须人工现场确认安全后才能手动恢复。上位机发个复位指令就重新启动设备——这在任何工厂都是红线。

我的项目里虽然没有独立的'安全 PLC'，但报警系统中处理了设备异常/断线/传感器故障的逻辑——本质上就是安全监控的思想：检测异常 → 通知操作员 → 记录可追溯。"
