核心概念：深入浅出生产者-消费者

为什么需要这个模式？

串口（RS485）是半双工的——同一时刻只能一个人说话。如果你发了请求 A 还没收到回复就发请求 B，两条消息在线上混在一起，谁都解不出来。

所以需要一个"调度员"来确保：发一个 → 等回复 → 再发下一个

类比：奶茶店

  • 生产者（点单员）：把订单贴到墙上 = Enqueue(request)
  • 队列（墙上的订单）：ConcurrentQueue<ModbusRequest>
  • 消费者（做奶茶的）：从墙上取一个订单，做完再取下⼀个 = 后台线程逐一处理

在你的系统里具体对应什么

生产者有两种：

  1. 定时器（自动）—— 每 100ms 自动把轮询请求放进队列
  2. 用户点击（手动）—— 点了"读取"按钮，也把请求放进同一个队列

消费者：一个后台线程，从队列里取出请求，通过 SerialPort 发送，等待响应，触发回调。

动手：关键代码

下面这段代码是你需要在项目中新增的核心——ModbusPollingService.cs：

using System.Collections.Concurrent;

public class ModbusRequest
{
    public byte DeviceAddr { get; }
    public byte FuncCode { get; }
    public ushort StartAddr { get; }
    public ushort Count { get; }
    public string Tag { get; }  // 比如 "PLC1_温度"
    // ...构造函数省略
}

public class ModbusPollingService : IDisposable
{
    private readonly ModbusTransport _transport;
    private readonly ConcurrentQueue<ModbusRequest> _queue = new();
    private readonly AutoResetEvent _signal = new(false);
    private CancellationTokenSource? _cts;
    private Task? _consumerTask;
    private Timer? _pollTimer;

    // 事件：当一帧数据解析完成后触发
    public event Action<ModbusRequest, ModbusParseResult>? DataReceived;

    public void Start()
    {
        _cts = new CancellationTokenSource();
        _consumerTask = Task.Run(() => ConsumerLoop(_cts.Token));
    }

    /// 添加轮询任务（生产者入口）
    public void Enqueue(ModbusRequest request)
    {
        _queue.Enqueue(request);
        _signal.Set();  // 唤醒消费者
    }

    /// 消费者线程：逐一取队列里的请求，发一个等一个
    private void ConsumerLoop(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            if (!_queue.TryDequeue(out var request))
            {
                _signal.WaitOne(100);  // 队列空了就等
                continue;
            }

            try
            {
                // 1. 发送请求（阻塞直到写完）
                var (frame, fc) = _transport.SendReadRequest(
                    request.DeviceAddr, request.FuncCode,
                    request.StartAddr, request.Count);

                // 2. 等一小段时间让数据收完（RTU 没有帧头标识长度）
                Thread.Sleep(50);

                // 3. 读取并解析响应
                // ★ 注意：这里需要给 Transport 加一个同步读方法
                byte[] response = ReadResponse(_transport, request.FuncCode, 2000);
                var result = ModbusProtocol.ParseResponse(response);
                // 4. 触发回调（UI 层通过 Invoke 订阅）
                DataReceived?.Invoke(request, result);
            }
            catch (Exception ex)
            {
                DataReceived?.Invoke(request, new ModbusParseResult
                {
                    IsError = true,
                    ErrorMessage = ex.Message
                });
            }
        }
    }

    public void Stop() { _cts?.Cancel(); _signal.Set(); }

    public void Dispose()
    {
        Stop();
        _cts?.Dispose();
        _signal.Dispose();
        _pollTimer?.Dispose();
    }
}
💡 面试亮点： "我的通信层使用了生产者-消费者模式，用 ConcurrentQueue + AutoResetEvent 实现了一个请求队列。消费者线程逐个发出请求并等待响应，天然解决了串口半双工的问题。所有新请求（不管是定时轮询生成的还是用户手动触发的）都走同一个队列，不会有指令打架。" —— 线程同步答到这个深度，面试官不会只给你开 8K。

第二个关键升级：超时重试策略

真实场景下，设备不可能永远在线。你需要处理：

  • 超时：发了请求 2 秒没回复→重试
  • 重试次数：连续 3 次失败→标记设备离线
  • 退避：失败后不要立刻重试，等 5 秒再试
public class DeviceState
{
    public byte Address { get; }
    public bool IsOnline { get; set; } = true;
    public int ConsecutiveFailures { get; set; }
    public DateTime? LastSuccessTime { get; set; }

    public bool ShouldSkip()
    {
        // 失败 3 次后，每 5 秒才重试一次
        if (ConsecutiveFailures < 3) return false;
        return (DateTime.Now - LastSuccessTime)?.TotalSeconds < 5;
    }

    public void RecordSuccess()
    {
        IsOnline = true;
        ConsecutiveFailures = 0;
        LastSuccessTime = DateTime.Now;
    }

    public void RecordFailure()
    {
        ConsecutiveFailures++;
        if (ConsecutiveFailures >= 3) IsOnline = false;
    }
}

{

    foreach (var cfg in _pollConfigs)
    {
        // 如果该设备当前在退避期，跳过
        if (_deviceStates[cfg.DeviceAddr].ShouldSkip())
            continue;

        _service.Enqueue(new ModbusRequest(
            cfg.DeviceAddr, cfg.FuncCode,
            cfg.StartAddr, cfg.Count, cfg.Tag));
    }

🔄 完整的轮询一次周期：

1️⃣ Timer 触发 → 遍历配置表 → 把 N 个请求入队

2️⃣ 消费者线程取出请求 A → 发帧 → 等响应 → 解析 → DataReceived 事件

3️⃣ 取出请求 B → 同上（不会和 A 抢线）

4️⃣ 所有请求处理完后线程阻塞等待新信号

5️⃣ 等待下一个 Timer tick，重复

面试官会怎么问？

🎙️ Q1：串口通信为什么要用队列？

"串口是半双工的，发送和接收不能同时进行。如果没有队列，两个请求同时发出会在线上碰撞，接收方无法区分数据边界。用 ConcurrentQueue + 单消费者线程，天然保证发一个等一个的时序。"

🎙️ Q2：如果某个设备一直不回复，会阻塞后续轮询吗？

"每个请求有超时时间（比如 2000ms）。超时后消费者线程会抛出异常，该设备被标记为离线并进入退避期（每 5 秒重试一次），不会阻塞后续设备的轮询。"

🎙️ Q3：ConcurrentQueue 和普通 Queue 有什么区别？

"ConcurrentQueue<T> 是 .NET 提供的线程安全队列，内部使用无锁算法（CAS），多个生产者可以同时入队而不需要手动加锁。普通 Queue<T> 在多线程环境下需要自己 lock，容易出错且性能更低。"

🎙️ Q4：AutoResetEvent 是干什么的？

"AutoResetEvent 是一个线程同步原语。当队列为空时，消费者线程通过 WaitOne() 阻塞自己，不占用 CPU。当新请求入队时，生产者调用 Set() 唤醒消费者。这是一种事件驱动的等待机制，比 while(true) 轮询更高效。"

A1 | 通信模式：单工 / 半双工 / 全双工

模式方向同时收发？类比技术实例
单工（Simplex） 单向❌ 只能单向 📢 广播喇叭 收音机、电视广播
半双工（Half-Duplex） 双向交替❌ 不能同时 📻 对讲机 RS485 串口、Modbus RTU
全双工（Full-Duplex） 双向同时✅ 可以 📞 电话 RS232、TCP 以太网
💡 面试话术： "Modbus RTU 走 RS485 是半双工，同一时刻只能有一帧在线上，所以请求必须串行排队发，一个一个来。这也是我为什么用生产者-消费者队列的根本原因——不是我想用，是物理层决定了必须这么做。Modbus TCP 走以太网是全双工，但 Modbus 协议层仍然是一问一答的，所以队列机制同样适用。"

A2 | 生产者-消费者模式（含完整可运行代码）

一句话总结： 点单的人（生产者）把订单贴在墙上（队列），做奶茶的人（消费者）从墙上取一个做一个，做完再做下一个。

在你的系统里具体是谁：

  • 生产者 1：定时器（Timer），每隔一段时间把轮询请求放进队列
  • 生产者 2：你手动点"读取"按钮
  • 队列：ConcurrentQueue<ModbusRequest>
  • 消费者：一个后台线程，从队列里取一个请求→发帧→等响应→解析→通知 UI

最小可运行代码（你之后可以直接用这个骨架）：

using System.Collections.Concurrent;

public class ModbusRequest
{
    public byte DevAddr { get; set; }
    public string Tag { get; set; } = "";
}

public class PollingService : IDisposable
{
    // ★ 1. 线程安全的队列——多个生产者同时放不怕
    private readonly ConcurrentQueue<ModbusRequest> _queue = new();

    // ★ 2. 信号灯——队列空了就让消费者睡觉，不白占 CPU
    private readonly AutoResetEvent _signal = new(false);

    private CancellationTokenSource? _cts;
    private Thread? _consumerThread;

    public event Action<ModbusRequest>? RequestProcessed;

    public void Start()
    {
        _cts = new CancellationTokenSource();
        _consumerThread = new Thread(() => ConsumerLoop(_cts.Token))
        {
            IsBackground = true,   // 主程序退出时自动结束
            Name = "Modbus消费者"
        };
        _consumerThread.Start();
    }

    // ★ 生产者入口——定时器和按钮都调这个方法
    public void Enqueue(ModbusRequest request)
    {
        _queue.Enqueue(request);    // 1. 放进队列
        _signal.Set();              // 2. 敲门叫醒消费者
    }

    // ★ 消费者循环——后台线程一直在跑这个
    private void ConsumerLoop(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            if (!_queue.TryDequeue(out var request))
            {
                // 队列空了→睡觉，等别人 Set() 叫醒我
                _signal.WaitOne(100);
                continue;
            }

            // 拿到一个请求，处理它
            Console.WriteLine($"处理设备 {request.DevAddr}...");
            Thread.Sleep(500);  // 模拟发帧 + 等回复

            // 通知外面（UI 层）
            RequestProcessed?.Invoke(request);
        }
    }

    public void Stop() => _cts?.Cancel();
    public void Dispose() { Stop(); _cts?.Dispose(); _signal.Dispose(); }
}

// 在你的 ModbusForm 里怎么用：
var service = new PollingService();
service.RequestProcessed += req =>
{
    this.Invoke(() => {
        box_recv.AppendText($"设备 {req.DevAddr} 数据已更新\r\n");
    });
};
service.Start();

// 无论是定时器还是按钮，都调这一个方法：
service.Enqueue(new ModbusRequest { DevAddr = 1, Tag = "温度表" });

A3 | AutoResetEvent 深度解析

它是新玩意吗？ 不是。它是 操作系统级别的内核事件对象，从 Windows NT 3.1（1993）就存在了。.NET 1.0（2002）开始就有包装。

为什么叫"Auto Reset"：

线程A 调用 WaitOne() → 阻塞等待
线程B 调用 Set()     → 门打开，放行一个等待线程
                      → 门自动关上（Auto Reset!）
线程A 再 WaitOne()   → 又得等下一次 Set()

对比 ManualResetEvent：
线程B 调用 Set()     → 门打开，放行所有等待线程
                      → 门一直开着，你得手动 Reset() 关上
AutoResetEventManualResetEvent
放行方式一次只放行一个放行所有等待线程
自动关闭✅ 放完自动关上❌ 得手动 Reset()
类比单人通过闸机大门敞开
适用场景生产者-消费者（一对一通知）一把初始化完叫醒所有等待者

Java 有对应的吗？

没有直接等价的 AutoResetEvent 类，但可以用其他方式模拟：

你需要的效果C#Java
一对一信号通知AutoResetEventSemaphore(1) 近似，或 synchronized + wait()/notify()
一对多信号通知ManualResetEventCountDownLatch / CyclicBarrier
限制并发数SemaphoreSemaphore
// Java 用 Semaphore 模拟 AutoResetEvent
Semaphore sem = new Semaphore(1);
sem.acquire();      // 消费信号 → WaitOne()
sem.release();      // 释放信号 → Set()

// Java 用 synchronized + wait/notify（更底层的等价物）
synchronized (lockObj) {
    while (queue.isEmpty()) {
        lockObj.wait();     // 阻塞等着 → WaitOne()
    }
}
// 另一个线程
synchronized (lockObj) {
    lockObj.notify();       // 叫醒一个 → Set()
}

前端有类似的吗？

有，但视角反了。AutoResetEvent 是线程级别的阻塞等待，前端是用回调/事件：

AutoResetEvent (C# 后端)前端等价物
等待WaitOne() — 线程挂起await / .then() — 不阻塞
通知Set() — 叫醒线程resolve / emit
等待期间CPU 完全释放事件循环继续跑

注意：Web Worker 场景下有 SharedArrayBuffer + Atomics.wait()，这是浏览器端真正能阻塞线程的机制，但极少用到。

💡 面试话术： "我选择 AutoResetEvent 有两个原因：第一，它是操作系统级别的内核对象，稳定可靠，二十多年历史；第二，它在队列空时通过 WaitOne 让线程完全阻塞不占 CPU，比 while(true) + Sleep 高效得多。C# 在这方面比 Java 用起来更简洁——Java 没有直接的等价类，需要自己用 Semaphore 或 synchronized + wait/notify 来模拟。"

A4 | CAS 无锁算法（Compare-And-Swap）

要解决什么问题？

多个线程同时修改同一个变量。传统做法是加锁（lock），但加锁意味着其他线程要排队等，有切换开销。

CAS 是什么？

用 CPU 的一条原子指令完成"检查-修改"两个动作：

// CAS 的语义伪代码：
bool CompareAndSwap(ref int location, int expectedValue, int newValue)
{
    if (location == expectedValue)    // 1. 看看现在是不是我预期的值
    {
        location = newValue;            // 2. 是？改成新值
        return true;                   // 3. 成功了
    }
    return false;                      // 被别人改了？重试
}

ConcurrentQueue 内部是怎么用的？

  1. 记下当前的队列尾巴位置
  2. 尝试 CAS 把尾巴指向新元素
  3. 如果失败（别的线程抢先改了尾巴）→ 重试第 1 步
  4. 如果成功 → 完事

整个过程无阻塞、无锁，抢不到的线程立刻重试而不是挂起。高并发下比 lock 快得多。

📌 你不需要自己实现 CAS： ConcurrentQueue、ConcurrentDictionary 内部已经用了 CAS，你直接调就行。了解 CAS 是为了在面试时能说清楚"为什么 ConcurrentQueue 比 Queue + lock 快"。

A5 | 退避策略（Backoff）详解

为什么需要退避？ 设备不响应时，如果你疯狂重试，可能把设备搞得更忙。你越急它越卡。

三档退避策略（从简单到进阶）：

策略规则适用场景
固定间隔 失败了等 5 秒再试 刚开始做，先跑通这个
线性退避 第 1 次等 1s，第 2 次等 2s，第 3 次等 3s…… 设备重启需要几秒到几十秒
指数退避 第 1 次等 1s，第 2 次等 2s，第 3 次等 4s，第 4 次等 8s…… 网络断开、服务器宕机（AWS 也用这个）
💡 面试话术（进阶）： "我用了指数退避——失败次数越多，重试间隔越长。第一次失败等 1 秒，第二次等 2 秒，第三次等 4 秒，以此类推，最大不超过 30 秒。这也是 AWS SDK 和 gRPC 的默认策略。一旦设备重新响应，立即重置退避计数器，恢复正常的轮询间隔。"
