一、问题回顾

1.1 I/Q 区直读不稳定 核心问题

S7-1200 通过 PUT/GET 读取过程映像区（I/Q）时有已知问题：

  • Snap7 的 TCP 缓冲区重传 bug — 断连后旧请求被重发，数据错乱
  • 不支持批量读取 — 超过实际存在的字节数就会超时断连
  • Q 区在部分固件上不支持 PUT/GET — S7AreaPA 返回错误码 5（TCP 接收超时）
  • 连接资源争抢 — 博途（PG）、威纶通（OP）、我们的 App 共用同一连接池

1.2 延迟高 体验问题

  • Snap7 逐字节读 I/Q：9 个 I 字节 + 9 个 Q 字节 = 18 次串行请求，耗时 ~500ms
  • 轮询间隔 2000ms，加上读取时间，实际更新延迟约 2.5 秒
  • 读写冲突时界面卡死

1.3 I/O 映射到 DB 不通 配置问题

  • 用户已将 I/Q 点映射到 DB5，但 DB5 读取返回 errCliAddressOutOfRange
  • 常见原因：DB 块开启了"优化的块访问"（Optimized block access）

二、解决方案

2.1 更换通信库：Snap7 → NodeS7 核心变更

维度Snap7（node-snap7js）NodeS7（nodes7）
架构底层 C++ 绑定包装纯 JS 实现 S7 协议
I/O 读写S7AreaPE / S7AreaPA 不稳定原生 I/Q 语法，自动优化
请求合并每个变量独立请求自动合并相邻地址为单个 S7 包
自动重连需手动实现内置自动重连

地址语法ReadArea + 区域常量字符串式：I0.0, QB2, DB1,REAL0.4

2.2 连接类型优化 稳定性

S7-1200 连接资源有限，3 种连接类型互不冲突：

类型值用途对应设备
PG0x01编程调试博途（TIA Portal）

BASIC0x03通用通信我们的 App（推荐）

2.3 批量读取 + 后台异步 性能

NodeS7 的 readAllItems 一次性读取所有已注册项：

  • I/O 字节（IB0~IB8、QB0~QB8）= 18 项
  • DB 配置变量 = 按需
  • DB 块 = 按需

自动合并为最优 S7 请求包，一次 round-trip 完成全部读取，延迟从 500ms 降到 ~20ms。

NodeS7 库深度解析

来源与背景

  • 作者：Dana Moffit（首版 2013 年）
  • GitHub：arnef/nodeS7
  • npm：nodes7（0.3.18，周下载 ~13k）
  • 许可证：MIT
  • 项目诞生于 Node.js 早期（v0.10 时代），目的是提供一个纯 JavaScript 实现、无需原生编译的西门子 S7 通信方案

协议原理

NodeS7 在 TCP 之上完整实现了 S7 通信协议栈：

应用层（我们的代码）
  ↕ 调用 readAllItems / writeItems
NodeS7 层
  ↕ ISO-on-TCP (RFC 1006)
TCP 层（端口 102）
  ↕
PLC

具体握手流程：

  1. TCP 连接 — 连 PLC 的 102 端口
  2. ISO 握手 — 发送连接请求 CR（Connect Request），包含本地/远程 TSAP，PLC 回复 CC（Connect Confirm）
  3. PDU 协商 — 协商最大 PDU 大小（S7-1200 通常 240~480 字节）和最大并行连接数
  4. S7 读写 — 构造 S7 协议数据单元（Header + Parameter + Data），通过 isoExchangeBuffer 发送并等待响应

核心架构

组件职责
NodeS7主类，管理连接生命周期、地址注册、读写队列
stringToS7Addr()将用户地址字符串（如 "IB3", "DB1,REAL0.4"）解析为内部 S7Item 结构体（区域/DB号/偏移/数据类型/长度）
S7Item内部地址描述对象，包含 addrtype（I/Q/M/DB）、datatype（X/B/W/I/R/DI/DW）、offset、bitOffset、arrayLength 等字段
prepareReadPacket()将 polledReadBlockList 中多个 S7Item 合并为最优的 S7 读取请求包。相邻地址自动合并为单次 ReadArea
prepareWritePacket()类似 prepareReadPacket，但构造写入包
translationCB翻译回调：用户自定义标签名 → S7 地址字符串。这是库的核心扩展点
addRemoveArray地址变更队列：addItems/removeItems 不立即生效，而是在下一次 readAllItems 调用时统一处理

自动优化（Auto-Optimization）

这是 NodeS7 相对 Snap7 最大的优势之一。当调用 readAllItems 时，prepareReadPacket 会执行：

  1. 排序 — 按区域（DB → I → Q → M）和偏移量排序所有待读地址
  2. 合并 — 相邻且同区域的地址合并为单个 ReadArea 请求。例如 IB0、IB1、IB2 合并为 "从 IB0 读 3 字节"
  3. 分包 — 若合并后的请求超过 PDU 大小，自动拆分为多个并行包
  4. 并行发送 — 多个包并行发送到 PLC（最大并行数由 PDU 协商决定）

效果：100 个分散的 bit 请求可能被合并为 2~3 个 S7 包，远优于 Snap7 的逐个读取。

与 Snap7 的协议层面差异

方面Snap7NodeS7
实现方式C++ 编写，Node.js 通过 N-API 绑定调用纯 JavaScript，从 TCP socket 开始逐字节实现 S7 协议
连接参数固定的 ISO 连接请求包，无法自定义支持自定义 localTSAP / remoteTSAP，灵活适配不同连接类型
PDU 大小硬编码 480 字节从 PLC 的 PDU 协商响应中解析，动态适配（240~960）
并行请求仅单 socket 串行支持 maxParallel（通常 3），多个包并行发送提高吞吐
读后恢复断连后需完全重建连接自动检测断连 → 重新 ISO 握手 → 重发待读队列
写位操作ReadArea 读字节 → 改位 → WriteArea 写回（手动实现）writeItems 内部处理读-改-写，但实测 Q 区 bit 不稳定，推荐写整字节

已知限制

  • 单维护者 — 自 2022 年后无更新，bus factor = 1
  • 不支持 S7 路由 — 不能通过一个 PLC 中转访问另一个 PLC
  • 不支持网卡绑定 — 没有 localAddress 参数，多网卡环境自动走默认路由
  • 无 TypeScript 定义 — 需要自己声明类型（项目中已封装）
  • 调试日志冗长 — 默认 debug 模式下输出到 stdout，需在实例化时设置 {silent: true}

六、遗留问题

  • DB5 读取失败 — 用户 I/Q 映射到 DB5，但返回 errCliAddressOutOfRange，需检查是否开启"优化的块访问"
  • 直读 I/Q 区偶发断连 — NodeS7 比 Snap7 稳定很多，但极速轮询（<100ms）仍可能导致连接不稳
  • 写 Q 位后的最终一致性 — 乐观更新与 PLC 实际值在写入失败时可能不一致，需下一次轮询修正
  • NodeS7 没有网卡绑定 — 不支持 localAddress 参数，多网卡环境无法指定用哪块网卡通信
