🖥️ Electron — 桌面端（Win/Mac/Linux）

架构方案

不需要分离前后端：Express 直接跑在 Electron 主进程 中，渲染进程加载 Vite 构建的静态页面。

┌─────────────────────────────────────────────┐ │ Electron 应用 │ │ ┌─────────────────────────────────────┐ │ │ │ Main Process (Node.js 22 + Express) │ │ │ │ ┌──────────┐ ┌──────────────────┐ │ │ │ │ │ Express │ │ better-sqlite3 │ │ │ │ │ │ API 服务 │ │ / node:sqlite │ │ │ │ │ │ :3001 │ │ S7 PLC 通信 │ │ │ │ │ └──────────┘ └──────────────────┘ │ │ │ └─────────────────────────────────────┘ │ │ ┌─────────────────────────────────────┐ │ │ │ Renderer Process (Vite React App) │ │ │ │ http://localhost:5173 或 file:// │ │ │ └─────────────────────────────────────┘ │ └─────────────────────────────────────────────┘

改造清单

改动项难度说明
项目结构 低 新增 electron/ 目录放主进程代码，保留现有 src/ 和 server/ 不变
Express 集成 低 在 Electron 的 app.on('ready') 回调中启动 Express，现有代码几乎零修改
Vite 构建 低 使用 electron-vite 或 @electron-forge/plugin-vite 零配置集成
better-sqlite3 中 需要 postinstall 脚本针对 Electron 重新编译；或用 node:sqlite 替代（推荐）
原生模块打包 中 需要 asarUnpack 配置 + 在 forge.config.ts 中用 packageAfterCopy hook 复制 .node 文件
S7 / OPC UA 通信 低 主进程直接使用 net.Socket 和现有 nodes7，无需改动
系统托盘 低 可添加托盘图标，后台运行时最小化到托盘
自动更新 中 使用 electron-updater，需要配置 S3/OSS 或 GitHub Releases

推荐工具链

🥇 electron-vite

  • 专门为 Vite + Electron 设计
  • 主进程、预加载、渲染进程分离配置
  • HMR 开发体验好
  • 社区活跃，文档齐全

🥇 Electron Forge

  • 官方打包/分发工具
  • 支持 .dmg / .exe / .deb / .rpm
  • 内置代码签名、自动更新
  • 推荐与 @electron-forge/plugin-vite 搭配

优劣总结

维度评价
✅ 优势 ① 改造量最小：Express + React 现有代码几乎零改动
② 原生 Node 模块直接可用
③ 社区成熟，踩坑资料丰富
④ 进程模型灵活（主/渲染分离自然适配前后端架构）
❌ 劣势 ① 安装包体积大（~150-250MB，含 Chromium）
② 内存占用高（~200-400MB）
③ 不支持触屏优化，移动端不可用
④ 打包配置稍繁琐（native modules + asar）
预估工期: 3~7 天
第 1 天：搭建 electron-vite 骨架，集成现有 src/server
第 2 天：配置 Vite 构建、HMR、better-sqlite3 兼容
第 3 天：窗口管理、系统托盘、原生菜单、打包测试

🦀 Tauri v2 — 桌面端（Win/Mac/Linux）

架构方案：两种路线

路线 A：Sidecar（侧边进程）— 推荐过渡方案

把 Express 后端用 pkg 打包成独立二进制，Tauri 通过 sidecar 机制启动。

┌─────────────────────────────────────┐ │ Tauri 应用 │ │ ┌──────────────────────────────┐ │ │ │ Rust Core + WebView │ │ │ │ (React Vite 构建的前端) │ │ │ └──────────────────────────────┘ │ │ ┌──────────────────────────────┐ │ │ │ Sidecar: Express Binary │ │ │ │ (pkg 打包的 Node.js 后端) │ │ │ └──────────────────────────────┘ │ └─────────────────────────────────────┘

路线 B：Rust 重写后端 — 最终推荐

用 Rust 重写 Express API 层，Tauri 命令直接调用 Rust 逻辑。

┌─────────────────────────────────────┐ │ Tauri 应用 │ │ ┌──────────────────────────────┐ │ │ │ Rust Backend (Axum/TauriCmd)│ │ │ │ ┌──────┐ ┌─────────────┐ │ │ │ │ │Axum │ │ rusqlite │ │ │ │ │ │HTTP │ │ S7 TCP Client│ │ │ │ │ └──────┘ └─────────────┘ │ │ │ └──────────────────────────────┘ │ │ ┌──────────────────────────────┐ │ │ │ WebView (React Vite 前端) │ │ │ └──────────────────────────────┘ │ └─────────────────────────────────────┘

Sidecar 方案改造清单

改动项难度说明
项目骨架 低 pnpm create tauri-app 初始化，保留现有前端
后端打包 中 用 yao-pkg/pkg 把 server/ 打包成可执行文件；原生模块如 better-sqlite3 需要预先编译
Sidecar 配置 低 tauri.conf.json 声明 externalBin + 权限配置
CORS 调整 低 开发模式前端 :5173 => 后端 :3001 的跨域已在 Vite proxy 中处理；生产环境 Tauri 前端从 WebView 加载 file:// 或 dev://，需调整 CORS
better-sqlite3 中 pkg 能打包但体积膨胀（~18MB+）；改用 node:sqlite 更轻量

Rust 重写改造清单

改动项难度说明
API 路由重写 高 Express 的 ~20 个路由端点需用 Rust (Axum/Actix) 重写；业务逻辑（报警引擎、趋势缓存、SSE）全部重写
SQLite 迁移 中 rusqlite 或 sqlx API 优秀，表结构和查询逻辑需移植
S7 PLC 通信 高 没有成熟的 Rust S7 库，需用 tokio::net::TcpStream 自行实现 ISO-on-TCP 握手 + S7 帧协议（约 300-500 行）
OPC UA 高 Rust 的 OPC UA 库 (opcua) 成熟度低于 node-opcua，可能需封装 FFI
SSE / WebSocket 中 用 tokio::sync::broadcast + Axum 的流式响应模拟 SSE

优劣总结

Sidecar 方案

  • ✅ 后端代码零改动
  • ⚠️ 包体积 ~80-120MB（含浏览器 + Node runtime）
  • ⚠️ pkg 对原生模块支持不完美
  • ✅ 开发周期短（1~2 周）

Rust 重写方案

  • ✅ 包体积 ~10-20MB（极小）
  • ✅ 性能最好，内存 ~50-100MB
  • ⚠️ 开发周期长（1~3 个月）
  • ⚠️ Rust 学习曲线

📱 Android 打包

架构方案

Android 无法直接运行 Node.js。有三种路线：

路线 A：Capacitor + 原生插件（推荐）

┌─────────────────────────────────────────────┐ │ Android App │ │ ┌─────────────────────────────────────┐ │ │ │ WebView (Capacitor) │ │ │ │ React Vite 前端 (几乎零修改) │ │ │ └─────────────────────────────────────┘ │ │ ┌─────────────────────────────────────┐ │ │ │ Native Plugins (Kotlin/Java) │ │ │ │ ┌────────────┐ ┌───────────────┐ │ │ │ │ │ Moka7 │ │ SQLite (原生) │ │ │ │ │ │ S7 通信 │ │ 本地存储 │ │ │ │ │ └────────────┘ └───────────────┘ │ │ │ └─────────────────────────────────────┘ │ └─────────────────────────────────────────────┘

前端用 Capacitor 跑在原生 WebView 中；后端逻辑用 Kotlin 写原生插件替代。启动后原生插件启动一个嵌入的 HTTP 服务器（如 NanoHTTPD）来提供 Express 替代 API。

组件Android 方案难度
前端Vite 构建 → Capacitor WebView，几乎零修改低
HTTP API用 NanoHTTPD 在原生侧启动轻量 HTTP 服务中
S7 PLC 通信Moka7（纯 Java，Snap7 官方移植）低
SQLite@capacitor-community/sqlite 或 原生 Room低
OPC UAPLC4X（Apache 企业级）或 Milo中
SSE 实时推送原生 HTTP Server 支持 SSE 标准中
react-grid-layout触屏需适配（拖拽事件变 touch 事件）中

路线 B：nodejs-mobile 嵌入 Node.js

将 Node.js 运行时嵌入 Android 应用，Express 后端作为后台线程运行。

组件方案难度
Node.js 运行时nodejs-mobile for Android（基于 Node 18）中
Express 后端在 Node 线程中原样运行，几乎零修改低
better-sqlite3需交叉编译 ARM 版本；或改用 node:sqlite（推荐）中
nodes7 / snap7需交叉编译 ARM 版 C++ 模块高
包体积增加 ~15-25MB（含 Node.js 运行时）中
维度Capacitor + 原生nodejs-mobile
后端代码复用需重写几乎零修改
前端代码复用几乎零修改几乎零修改
S7 通信Moka7（纯 Java，成熟）交叉编译 snap7 for ARM
包体积增量~5MB（插件）~15-25MB（含 Node）
开发周期2~4 周1~3 周
App Store 审核风险无可能有（iOS 侧）

🍎 iOS 打包

核心问题

iOS 是打包难度最高的平台，原因：

  • 无 Node.js 运行时 — Apple 不允许在 App Store 应用中动态加载 JavaScript 引擎执行任意代码
  • 无 S7 通信库 — 目前没有成熟的 Swift / Obj-C S7 PLC 库
  • 严格的网络沙箱 — 后台进程受限，长时间 TCP 连接需特殊配置
  • App Review 不确定性 — 内嵌 Node.js 的应用被拒风险高

改造清单

组件方案难度
前端Capacitor WebView，React 代码零修改低
HTTP APISwift 启动 Vapor / Kitura 嵌入式 HTTP 服务器，或用 GCDWebServer高
S7 PLC 通信Swift 原生实现 ISO-on-TCP + S7 帧协议（使用 NWConnection）高
SQLite@capacitor-community/sqlite 或 原生 GRDB.swift低
OPC UA无成熟 Swift 库，需 FFI 调用 C 库或封裝 C++高
SSE / 实时推送Swift URLSession 或原生 HTTP Server 支持中
react-grid-layout 触屏需适配 iOS 触屏拖拽事件中
包体积~30-50MB中
iOS 改造难度
高 — 预估 1~3 个月

结论：除非有强 iOS 需求，否则不建议现阶段投入。 如确实需要，先用 Capacitor 跑通前端，后端 API 逐步用 Swift 重写。

第一阶段：Electron 桌面端（3~7 天）

为什么先做 Electron？
✅ 后端 100% 复用、前端 100% 复用
✅ 改造成本最低，3-7 天可出 MVP
✅ 原生模块（snap7、better-sqlite3）直接可用
✅ 覆盖 Windows / macOS / Linux 三大桌面平台
✅ 为后续向 Tauri 迁移保留干净的架构边界

第二阶段：Tauri Rust 重写（长远规划）

什么时候迁移？
✅ 当需要大幅减小安装包体积时（如分发到低带宽场景）
✅ 当需要更低的内存占用时（如边缘网关设备）
✅ 当团队有 Rust 能力后

💡 关键建议

🏆 最高性价比方案
Electron + node:sqlite
Node.js 22 内置 node:sqlite（自 v22.13 正式稳定），可完全替代 better-sqlite3，
零原生依赖、零编译、零打包问题。这是通往 Electron 的最短路径。
💡 前端触屏适配
react-grid-layout 支持 isTouch 属性，
只需设置 isDraggable: true, useCSSTransforms: true
即可在触屏设备上拖拽。mobile 下增加组件间距（~16px）即可。
💡 代码复用策略
将 shared/types.ts 保持为纯 TypeScript，
不引入 Node 或浏览器 API。
这样 Electron / Tauri / Mobile 均可共享类型定义。
💡 分发渠道
Electron: GitHub Releases + 私有更新服务器
Android: 侧载 APK / 企业分发 / Play Store
iOS: 仅企业证书分发（TestFlight 对内）
💡 PLC 通信的跨平台方案
最佳统一方案：将 S7 通信抽成 独立库/模块
桌面用 nodes7 / snap7，Android 用 Moka7（API 设计几乎一致），
iOS 需自实现。这些库都基于同一协议标准，接口风格类似。
