三、AlarmItem.cs — 数据模型增强

改动原因

原有的 AlarmItem 模型过于简单：手写 INPC（被项目规范禁止）、缺少工控场景必要的字段（区域、死区、搁置、报警类型等）、无法序列化到 JSON 做持久化。

具体变更

类别变更说明
基类 改 从手写 INotifyPropertyChanged 改为继承 ObservableObject + [ObservableProperty] 源生成器
新增 + AlarmConditionType 枚举：High、HighHigh、Low、LowLow、NotEqual、RateOfChange、Digital
新增 + Area 属性 — 所属区域/工段/设备组，用于分组过滤
新增 + Deadband 死区宽度 — 防抖核心参数
新增 + IsShelved + ShelvedBy + ShelvedUntil — 报警搁置状态
新增 + Comment — 操作员备注
新增 + Duration 计算属性 — 报警持续时长
新增 + NeedsFlash 计算属性 — 严重未确认报警标记
新增 + DateTimeText 完整日期 + DeadbandLow/High 滞回区间

为什么用 ObservableObject

项目规范要求在 Models 中使用 ObservableObject + [ObservableProperty] 源生成器：

  • 禁止手写 INotifyPropertyChanged
  • 禁止"半 INPC"（部分通知部分不通知）
  • 源生成器自动生成属性 + 通知代码，减少手写错误

死区原理

值 ──┬────────────────┐
     │                │
阈值 ┼────────────────┼────
     │    ←死区→       │
     │  ┌──────────┐   │
     │  │ 不回切    │   │
     └──┴──────────┴───┘
  报警┌──────────────────┘ 稳定恢复

触发条件：值 > 阈值 + 死区（从正常到报警）
恢复条件：值 < 阈值 - 死区（从报警到正常，防止临界抖动）

OnDelay/OffDelay 原理

正常 ──┬─────────────────────────┬────
       │                         │
       │  条件满足                │  条件恢复
       │  ┌── OnDelay ──┐        │  ┌── OffDelay ──┐
       │  │ 等待 N ms   │        │  │ 等待 N ms   │
       v  v             v        v  v             v
报警 ────────────────────────────── ────────────────────
                             触发报警              恢复报警

八、DB 变量类型化解码 — 新增功能

改动原因

原有的 DbPollItem 只有 Length（字节数），PollingScheduler 按字节逐个存到 _lastValues，AlarmService 只读单个 byte 做阈值比较。对于 DB 中的 REAL/LREAL/INT/DINT 等多字节类型，读到的只是第 1 个字节（0~255），无法做正确的浮点数/整形比较。

解决方案

  • DbPollItem.DataType — 新增字符串属性，声明 PLC 数据类型
  • DbPollItem.EffectiveLength — 根据 DataType 自动推导应读的字节数，不用再手动设 Length
  • PollingScheduler._typedValues — 新增 ConcurrentDictionary<string, double> 存放解码后的值
  • PollingScheduler.GetDoubleValue(key) — 优先查 _typedValues，没有再回退到 byte
  • AlarmService.OnDataUpdated — 改用 GetDoubleValue()，阈值比较使用真实浮点数

支持的数据类型

DataType字节数解码方法说明
BYTE使用 Lengthbuf[0]原行为，单字节
WORD / INT2S7.GetWordAt / S7.GetIntAt无符号/有符号 16 位
DINT / REAL4S7.GetDIntAt / S7.GetRealAt32 位整数 / 单精度浮点
LREAL8BitConverter.ToDouble (大端)64 位双精度浮点

Key 格式

类型化解码后的值以 DB{DbNumber}:{Offset} 格式存入 _typedValues。AlarmRule.VariableKey 填入同样的 key 即可触发报警检测。

DbPollItem: DbNumber=1, Offset=6, DataType="REAL"    → key = "DB1:6"
AlarmRule:  VariableKey="DB1:6", Threshold=200, Condition=Above

旧的 DB1[6] 格式（单字节 key）仍然保留，与新的 typed key 互不干扰。

九、数据类型 UI 集成 — 第四轮

改动原因

第三轮添加了 DbPollItem.DataType 和 PollingScheduler 类型化解码，但用户仍需要手动写代码创建 DbPollItem 实例才能开始轮询。报警规则的 UI 编辑表单也没有 DataType 字段，DB 类型变量无法在 UI 中完整配置。

解决方案

  • AlarmRule 新增 DataType 属性 — 默认 "BYTE"，与 DbPollItem 对齐
  • ViewModel 新增 EditDataType — 编辑表单绑定属性，提供 EditDataTypeOptions 下拉列表（BYTE/WORD/INT/DINT/REAL/LREAL）
  • XAML 编辑表单重构 — 第一行改为「变量名 | 数据类型 | 级别 | 报警类型」，描述下移到第三行
  • 规则列表新增 DataType 列 — 每条规则直观显示数据类型
  • SyncDbPollItem() 自动同步 — 保存规则时，若 VariableKey 是 DB{N}:{O} 格式，自动创建或更新对应的 DbPollItem：

高级用法：代码添加规则

通过 UI 保存规则时会自动创建 DbPollItem，但代码添加规则时仍需手动配置 DbPollItem：

// ===== I/Q/M 单字节 (原行为) =====
alarmService.AddRule(new AlarmRule
{
    VariableKey    = "I0",              // I0 单字节
    Description    = "I0 高限报警",
    Severity       = AlarmSeverity.Critical,
    ConditionType  = AlarmConditionType.High,
    Threshold      = 200,
    Deadband       = 5,
    OnDelayMs      = 1000,
    OffDelayMs     = 2000,
    Area           = "反应釜A",
    IsEnabled      = true,
});

// ===== DB 多字节 (REAL/DINT/LREAL/INT/WORD) =====
// 先配置 DbPollItem
config.DbItems.Add(new DbPollItem
{
    DbNumber = 1,                        // DB1
    Offset   = 6,                        // 从字节 6 开始
    DataType = "REAL",                   // 自动读 4 字节，解码为 float
    Enabled  = true,
});
// 再添加报警规则，key 格式 DB{DbNumber}:{Offset}
alarmService.AddRule(new AlarmRule
{
    VariableKey    = "DB1:6",            // 对应 DB1 偏移 6 的 REAL 值
    Description    = "反应釜A温度高限",
    Severity       = AlarmSeverity.Critical,
    ConditionType  = AlarmConditionType.High,
    Threshold      = 200,
    Deadband       = 5,
    OnDelayMs      = 1000,
    OffDelayMs     = 2000,
    Area           = "反应釜A",
    IsEnabled      = true,
});

代码添加的规则会自动出现在 UI 列表中，反之亦然。

十一、常见问题

Q: 为什么点「启动监控」后没有报警产生？

A: 因为还没有添加任何报警规则。必须先「⚙ 规则管理」→「＋ 添加规则」，指定变量名和阈值。

Q: 报警老是一闪一闪地反复触发/恢复怎么办？

A: 给规则设置死区（Deadband）和触发延时（OnDelayMs）。死区推荐 2-5%，OnDelay 推荐 500-1000ms。

Q: 重启程序后报警记录还在吗？

A: 在。报警历史保存到 %APPDATA%\KesaPlc\alarms.json，规则保存到 rules.json，启动时自动加载。

Q: 我可以用代码一次性添加很多规则吗？

A: 可以。在任意位置多次调用 alarmService.AddRule() 即可，它们会与 UI 添加的规则合并显示。

Q: 报警列表最多能存多少条？

A: 内存默认 1000 条，持久化最多 10000 条。超过上限时删除最早的。

Q: 导出的 CSV 打不开怎么办？

A: CSV 是 UTF-8 编码。Excel 打开时如果乱码，用"数据 → 自文本/CSV"导入，选择 UTF-8 编码。

Q: 怎么关掉规则管理面板？
