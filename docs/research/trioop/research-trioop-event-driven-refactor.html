一、先看问题：你现在的代码长什么样

打开你的 server/index.ts，第 848~883 行的 poll() 函数：

async function poll() {
  // ⚠️ 1. 检查连接（可能尝试重连）
  if (!plc.isConnected()) { ... }
  if (!plc.isQueueIdle()) return  // ⚠️ 写入队列忙时跳过

  // ⚠️ 2. 读取 PLC（核心任务）
  const result = await plc.readOnce()

  // ⚠️ 3. 更新 5 个全局缓存
  plcDataCache = result.db
  ioDataCache.i = result.io.i
  ioDataCache.q = result.io.q
  ioDataCache.m = result.io.m
  dbBlockCache = result.dbBlocks

  // ⚠️ 4. 推送到趋势缓冲区
  const trendVals = /* 遍历提取 */
  trendBuffer.push(trendVals)

  // ⚠️ 5. 写入 SQLite 历史库
  writePoints(trendVals)

  // ⚠️ 6. 检查报警规则
  checkAlarms(trendVals)

  // ⚠️ 7. 广播给所有 SSE 客户端
  broadcast({ db: plcDataCache, io: ioDataCache, dbBlocks: dbBlockCache })
}

还有 OPC UA 模式下 一模一样的重复逻辑（第 248~263 行 startOpcuaBroadcast()）：

function startOpcuaBroadcast() {
  opcuaBroadcastTimer = setInterval(() => {
    const cache = opcua.getValueCache()
    // ⚠️ 再次：趋势存储 + 历史写入 + 报警检查 + 广播
    trendBuffer.push(cache)
    writePoints(cache)
    checkAlarms(cache)
    broadcast({ db, io: { i: {}, q: {}, m: {} }, dbBlocks: {} })
  }, 200)
}

1.1 这么写有什么问题？

#问题真实的后果
1 一个函数干所有事 想加一个新功能（比如把数据记到日志文件），你必须修改 poll() 函数本身。改动有风险——改错了整条数据链路断掉。
2 一个 consumer 抛异常，整条链路挂 如果 writePoints() 因为 SQLite 磁盘满了而抛异常，整个 poll() 的 catch 会吞掉，SSE 广播也发不出去——前端看到的数据冻住了。
3 S7 模式 + OPC UA 模式各写一遍 两个 setInterval 里写了几乎一样的 trendBuffer.push + writePoints + checkAlarms + broadcast。改一个忘了改另一个，两边行为不一致。
4 没法单独测试 怎么测试"报警规则正确触发"？必须: 连真的 PLC → 启动轮询 → 等数据变化 → 等 checkAlarms 被调用。不能独立地 mock 数据喂给报警引擎。
5 加新数据源必须重写一遍 如果以后加了 MQTT 数据源、或从 HTTP API 拉数据，得再写第三个 setInterval 循环，再复制一遍 trendBuffer.push + writePoints + checkAlarms + broadcast。

二、事件驱动：改成什么样？

2.1 核心思路

改动前（紧耦合流水线）： 定时器 → readOnce() → 更新缓存 → 存趋势 → 写历史 → 查报警 → 推SSE ↓ 全部在 poll() 一个函数里 一个挂了全都挂 改动后（事件总线）： ┌───────────── 推SSE (sse.ts) │ 定时器 → emit('data') ─┼──────── 存趋势 (ringBuffer.ts) │ ├──────── 写历史 (historyStore.ts) │ └──────── 查报警 (alarmEngine.ts) 新的消费者（比如记日志）: │ └──────── 记日志 ← 独立文件，不碰 poll()

2.2 需要改动的文件

文件改动行数
新建 server/eventBus.ts创建一个 EventEmitter 实例 + 类型定义~10 行
server/index.ts把 poll() 拆成"采集 + emit"两步~30 行（删 50 加 20）
server/sse.ts加一个 data 事件监听，替代 broadcast 调用~5 行
server/ringBuffer.ts加一个 data 事件监听（可选方案）~5 行

2.3 新建文件：eventBus.ts

// server/eventBus.ts — 全局事件总线
import { EventEmitter } from 'events'
import type { PLCData } from '../shared/types.js'

/** poll() 采集完一轮数据后 emit 的 payload 类型 */
export interface PlcDataEvent {
  /** DB 变量：变量名 → { value, type, ... } */
  db: PLCData
  /** I/Q/M 区字节 */
  io: { i: Record<number, number>; q: Record<number, number>; m: Record<number, number> }
  /** DB 块原始字节 */
  dbBlocks: Record<string, number[] | null>
  /** 时间戳（毫秒） */
  timestamp: number
  /** 数据源标识 */
  source: 's7' | 'opcua'
}

// 单例 EventEmitter
const bus = new EventEmitter()

// 给事件名定义一个常量（防止拼写错误）
export const PLC_DATA_EVENT = 'plc:data'

export { bus }

2.4 改动 index.ts：poll() 函数

❌ 改动前（紧耦合）

async function poll() {
  // ...检查连接...
  const result = await plc.readOnce()

  // ⚠️ 更新缓存（poll 自己管）
  plcDataCache = result.db
  ioDataCache.i = result.io.i
  ioDataCache.q = result.io.q
  ioDataCache.m = result.io.m
  dbBlockCache = result.dbBlocks

  // ⚠️ 趋势
  const trendVals = /* 提取 */
  trendBuffer.push(trendVals)

  // ⚠️ 历史
  writePoints(trendVals)

  // ⚠️ 报警
  checkAlarms(trendVals)

  // ⚠️ 推 SSE
  broadcast({ db: plcDataCache, ... })
}

✅ 改动后（事件驱动）

async function poll() {
  // ...检查连接...  (不变)
  const result = await plc.readOnce()

  // ✅ 缓存照常更新（保持兼容）
  plcDataCache = result.db
  ioDataCache.i = result.io.i
  ioDataCache.q = result.io.q
  ioDataCache.m = result.io.m
  dbBlockCache = result.dbBlocks

  // ✅ 只做一件事：emit 事件
  //    所有消费者各自监听 'plc:data'
  bus.emit(PLC_DATA_EVENT, {
    db: result.db,
    io: result.io,
    dbBlocks: result.dbBlocks,
    timestamp: Date.now(),
    source: 's7',
  })
}

poll() 从 35 行降到 15 行。不再直接调 trendBuffer、writePoints、checkAlarms、broadcast。它只管采集和缓存，后面的活谁爱干谁干。

新建 historySubscriber.ts — 独立文件负责历史存储

// server/historySubscriber.ts
import { bus, PLC_DATA_EVENT, type PlcDataEvent } from './eventBus.js'
import { writePoints } from './historyStore.js'
import { trendBuffer } from './ringBuffer.js'

bus.on(PLC_DATA_EVENT, (data: PlcDataEvent) => {
  // 从 db 中提取数值
  const vals: Record<string, number | boolean> = {}
  for (const [name, pt] of Object.entries(data.db)) {
    vals[name] = pt.value
  }

  // ✅ 各自 try-catch，互不影响
  try { trendBuffer.push(vals) } catch (e) {
    console.error('[趋势] 写入失败:', e)
  }
  try { writePoints(vals) } catch (e) {
    console.error('[历史] 写入失败:', e)
  }
})

2.6 OPC UA 模式的重复循环也消灭了

改之前的 startOpcuaBroadcast() 里面写了几乎和 poll() 一样的 4 件事。改之后：

// index.ts — OPC UA 定时器也改成 emit 事件

  stopOpcuaBroadcast()
  opcuaBroadcastTimer = setInterval(() => {
    const cache = opcua.getValueCache()
    // ✅ 同样 emit 同一个事件，所有消费者自动触发

不再需要两个地方写同样的趋势/报警/广播代码。消费者监听一次，无论数据从 S7 来还是 OPC UA 来，统一处理。

三、改动前后对比总结

维度改动前改动后
poll() 函数行数~35 行（读 + 缓存 + 趋势 + 历史 + 报警 + SSE）~15 行（读 + 缓存 + emit）
轮询代码 + OPC UA 代码重复两份相同的趋势+历史+报警+广播逻辑一份监听，两个数据源共用一个消费者
加新功能修改 poll() 函数新建一个文件，加一行 bus.on(...)
链路上一个环节挂了整条链路断，SSE 广播也发不出各自 try-catch，互不影响

新增数据源（比如未来加 MQTT）再写第三个 setInterval，再复制一次读完后 emit 同一个事件，现有的消费者自动处理

四、收益 vs 副作用 vs 消除方法

4.1 收益

#收益为什么重要
1 可维护性质的提升 以后加任何新功能（日志、统计、WebSocket 升级、数据导出），新建一个文件 + 一行 bus.on。不需要动 poll()，零风险。
2 一个环节挂了不影响其他 现在 writePoints() 抛异常 → SSE 也发不出去了。改后各自 try-catch，SQLite 满了报警照跑、SSE 照推。
3 消除代码重复 S7 poll() 和 OPC UA setInterval 各写了一套 trendBuffer.push + writePoints + checkAlarms。改后写一次监听，两个数据源通吃。
4 单元测试可行 直接 bus.emit 伪造数据就能测报警引擎、历史存储，不需要连 PLC。
5 为 WebSocket 升级铺路 现在你的 SSE 在 index.ts 里调 broadcast()。改成事件驱动后，加一个 WebSocket 推流就是新建一个文件 + 一行 bus.on。

4.2 副作用

#副作用严重程度消除方法
A 事件监听器执行顺序不确定 低 EventEmitter 在 Node.js 中默认按注册顺序同步执行，所以顺序是确定的（先注册的先跑）。如果确实需要保证"先存历史再查报警"，可以在一个监听器里按顺序调，或者用 bus.listeners() 控制。

但一般来说不需要——趋势/历史/报警/SSE 之间没有顺序依赖。
B 监听器忘记 remove 可能导致内存泄漏 中（长期运行） 你的应用是单进程长期运行，这些监听器注册后永远不会移除。Node.js EventEmitter 对这种情况没有内存泄漏——监听器函数只有一份引用。但如果你在动态模块热加载（如 Vite HMR），每次重新 import 会注册新的监听器。

✅ 解决方案：在 eventBus.ts 中加 bus.setMaxListeners(50)，以及在每次启动时清理旧监听器：bus.removeAllListeners(PLC_DATA_EVENT)
C try-catch 可能静默吞掉错误 低（但要注意） 每个监听器自己 try-catch 是设计意图（互不影响），但要用 console.error 打印出来，不能让错误无声消失。

✅ 解决方案：在 catch 块里用 console.error('[xxx] ...', e) + 记入诊断模块的 recordError()。不改现有诊断逻辑。
D 无法一眼看到整条数据链路 低（习惯问题） 原先 poll() 里 35 行顺序执行，一目了然。改成事件驱动后，谁监听了这个事件要去各个文件里找。这是事件驱动架构天生的权衡。

✅ 解决方案：在 eventBus.ts 里加一个注释块列出所有监听器：
// plc:data 监听器列表：
// - sse.ts (推送给前端)
// - historySubscriber.ts (存趋势 + 历史)
// - alarmSubscriber.ts (检查报警)
E EventEmitter 背压问题 低（当前场景） 如果某个监听器处理得慢（比如 writePoints 写 SQLite 耗时 200ms），而 poll() 每 500ms emit 一次，会造成事件积压。EventEmitter 是同步的，所以会阻塞后续监听器。

✅ 解决方案：把慢的监听器改为异步（setImmediate 或 queueMicrotask）：
bus.on(PLC_DATA_EVENT, (data) => {
setImmediate(() => { try { writePoints(...) } catch {} })
})
这样事件循环会先执行完所有同步监听器（SSE 推送），再去处理异步的任务（SQLite 写入）。

五、50ms 轮询下的背压分析——你最关心的问题

先说结论：50ms（20次/秒）轮询，纯 EventEmitter 同步监听器完全扛得住。 SQLite 写操作需要加串行队列，但方案很简单。往下看详细分析。

5.1 每个 50ms 周期里发生了什么

时间线 (50ms = 20次/秒):

0ms    poll() 开始 → readOnce() 发出 S7 请求
      ↓ (等待网络，约 2~10ms)
10ms   readOnce() 返回数据
      ↓
10ms   emit('plc:data')
      ↓  (同步执行以下全部监听器)
10ms   → SSE broadcast      (0.01ms, 纯内存)
10ms   → trendBuffer.push   (0.001ms, 纯内存环形缓冲区)
10ms   → checkAlarms        (0.1ms, 纯内存比对)
10ms   → writePoints        (启动异步 SQLite 写入, ~5~20ms)
      ↓
10.1ms poll() 返回，事件循环空闲
      ↓
50ms   下一轮 poll() 开始
      ↓
60ms   writePoints 完成（在后台事件循环中跑完）

关键发现：前三个监听器（SSE、趋势、报警）都是纯内存操作，耗时加起来 < 0.2ms，50ms 间隔对它来说像散步。唯一可能拖后腿的是 writePoints（SQLite 写入）。

5.2 SQLite 写入压力测试

轮询间隔事件/秒SQLite 写入/秒SQLite 能否承受？
500ms（当前）22✅ 散步级别
100ms1010✅ SQLite WAL 模式单线程写可达 ~50K ops/s
50ms（你问的）2020✅ 20 次/秒对 SQLite 来说跟没负载一样
10ms100100⚠️ 仍远低于 SQLite 上限，但 EventEmitter 同步循环可能卡
1ms10001000❌ 需要批量写入 + 背压控制

SQLite 在 WAL 模式下的写入能力：

  • 简单 INSERT：~50,000~80,000 行/秒（单线程）
  • 有索引的 INSERT：~10,000~20,000 行/秒
  • 事务批量写（1000条/事务）：~200,000 行/秒

你 50ms 轮询 = 20 次 INSERT/秒，是 SQLite 能力的 0.04%。SQLite 甚至不会注意到这个负载。

5.3 真正需要担心的不是 SQLite，是"回调地狱"

你们现在的 writePoints 可能长这样（伪代码）：

// 现在的 writePoints（典型的 SQLite 写入）
export function writePoints(vals: Record<string, number | boolean>) {
  const stmt = db.prepare('INSERT INTO history VALUES (?, ?, ?)')
  for (const [name, value] of Object.entries(vals)) {
    stmt.run(Date.now(), name, value)  // 同步 SQLite，~0.05ms/行
  }
}

如果用的是 better-sqlite3（同步 API），那 writePoints 是同步的——EventEmitter 会完全执行完它再往下走。50ms 写入 ~50 个变量，总耗时也就 ~2.5ms，完全 OK。

如果用的是 sql.js 或异步 SQLite 库，那 writePoints 是 async 的——EventEmitter 会切到下一个监听器。这时潜在的问题是：

50ms 轮询 + 异步 writePoints 的风险： 事件 #1 (0ms) → writePoints 开始 → 还没写完 事件 #2 (50ms) → writePoints 开始 → 两个同时写！ 事件 #3 (100ms) → writePoints 开始 → 三个同时写！ ... SQLite 抛出 SQLITE_BUSY → 错误被静默吞掉 → 历史数据丢失

5.4 解决方案（代码已备好，你们改的时候直接抄）

方案 A：串行队列（推荐，保留写入顺序，适用于所有轮询间隔）

// server/historySubscriber.ts
import { bus, PLC_DATA_EVENT, type PlcDataEvent } from './eventBus.js'
import { writePoints } from './historyStore.js'
import { trendBuffer } from './ringBuffer.js'

// ── 串行写入队列 ──────────────────────────
const queue: PlcDataEvent[] = []
let busy = false

async function flush() {
  if (busy || queue.length === 0) return
  busy = true
  const data = queue.shift()!

  const vals: Record<string, number | boolean> = {}
  for (const [name, pt] of Object.entries(data.db)) {
    vals[name] = pt.value
  }

  try {
    trendBuffer.push(vals)        // 纯内存，同步
    await writePoints(vals)       // SQLite，可能异步
  } catch (e) {
    console.error('[历史] 写入失败:', e)
  }

  busy = false
  flush()  // 处理队列中下一个
}

// 监听事件：入队 + 触发处理
bus.on(PLC_DATA_EVENT, (data: PlcDataEvent) => {
  queue.push(data)
  if (!busy) flush()
})

// 可选：队列溢出保护（防止 poll 比 SQLite 快太多时内存疯长）
const MAX_QUEUE = 100
bus.on(PLC_DATA_EVENT, (data: PlcDataEvent) => {
  if (queue.length > MAX_QUEUE) {
    // 队列满了：丢弃最旧的事件（保留最近的数据）
    queue.splice(0, queue.length - MAX_QUEUE)
    console.warn(`[历史] 队列溢出，丢弃 ${queue.length - MAX_QUEUE} 个旧事件`)
  }
  queue.push(data)
  if (!busy) flush()
})

方案 B：丢弃旧事件，保留最新（适合只关心最新状态的趋势图）

// 更激进：只保留最后一个事件的值
let latestValues: Record<string, number | boolean> = {}
let writing = false

bus.on(PLC_DATA_EVENT, (data: PlcDataEvent) => {
  // 永远用最新的覆盖
  for (const [name, pt] of Object.entries(data.db)) {
    latestValues[name] = pt.value
  }
  if (!writing) doWrite()
})

async function doWrite() {
  writing = true
  while (Object.keys(latestValues).length > 0) {
    const batch = latestValues
    latestValues = {}  // 清空，新的数据会累积进来
    try {
      await writePoints(batch)
    } catch (e) {
      console.error('[历史] 写入失败:', e)
    }
  }
  writing = false
}
// ✅ 无论多快轮询，writePoints 永远不会并发，且总是写入最新值

5.5 结论：50ms 到底用不用操心？

轮询间隔背压风险你需要做什么
500ms（当前）❌ 不存在什么都不用做
100ms❌ 不存在什么都不用做
50ms⚠️ 取决于 writePoints 是否异步如果同步（better-sqlite3）：什么都不用做
如果异步：加 ~20 行串行队列代码
10ms⚠️ 需要串行队列用上面方案 A，串行 + 溢出保护
< 5ms✅ 需要丢弃旧事件用方案 B，只写最新值

对你来说：先改事件驱动架构，轮询还是 500ms。以后要降到 50ms 的时候，再回来加这 20 行串行队列代码。不需要现在做。

注意：以上分析假设 writePoints 用的是 better-sqlite3（同步 API）。如果是 sql.js 或其他异步 SQLite 库，请先确认实际 API。

七、EventEmitter 背压问题详解（通用）

上面谈的是你具体的 50ms 场景，这里再补充背压的一般原理：

7.1 问题场景

bus.on(PLC_DATA_EVENT, async (data) => {
  // 这个监听器是 async 的
  await writePoints(data)  // SQLite 写入，可能耗时 100~500ms
  // EventEmitter 不会 await 它！下一个监听器还是同步触发
})

bus.on(PLC_DATA_EVENT, (data) => {
  // 这个监听器在第一个 await writePoints 之前就同步执行了
  // 但如果第一个监听器有 await 前的同步代码且很慢，会阻塞这里
  broadcast(data)
})

实际上 EventEmitter 对 async 监听器的行为是：同步执行到第一个 await，然后切到下一个监听器。所以不会因为一个慢的 async 监听器阻塞其他监听器。

但真正的问题是：

  • 如果 poll() 每 500ms emit 一次，而 writePoints 每次耗时 600ms
  • 第二个事件来的时候，第一个 writePoints 还没跑完
  • 它们在竞争 SQLite 连接——卡死、或抛出 SQLITE_BUSY

7.2 解决方案

对 Trioop 当前的数据量（几十个变量，500ms 轮询），writePoints 通常 < 10ms，根本不会遇到这个问题。但如果以后轮询间隔很短（100ms）或数据量大，有两个解法：

方案 A：队列串行化（推荐，保留写入顺序）

import { EventEmitter } from 'events'

function createSerialSubscriber() {
  const queue: PlcDataEvent[] = []
  let busy = false

  async function process() {
    if (busy || queue.length === 0) return
    busy = true
    const data = queue.shift()!
    try {
      const vals = extractValues(data)
      await writePoints(vals)
      await trendBuffer.push(vals)
    } catch (e) {
      console.error('[历史] 写入失败:', e)
    }
    busy = false
    process()  // 处理下一个
  }

  return (data: PlcDataEvent) => {
    queue.push(data)
    process()
  }
}

bus.on(PLC_DATA_EVENT, createSerialSubscriber())
// ✅ 多个事件排队写入，不会同时写 SQLite

方案 B：使用 p-limit 控制并发

import pLimit from 'p-limit'
const limit = pLimit(1)  // 最多 1 个并发

bus.on(PLC_DATA_EVENT, (data) => {
  limit(async () => {
    const vals = extractValues(data)
    await writePoints(vals)
  })
})

对你们当前场景，什么都不用做——500ms 轮询 + 几十个变量，writePoints 在 10ms 内完成，不存在背压问题。上面这些只是让你知道万一以后遇到怎么解决。

八、总结与操作步骤

✅ 改动的本质：把 poll() 从"采集 + 处理"拆成"采集 → 事件 → 处理"。 poll() 只管读数据和更新缓存，处理工作交给独立的监听器。 ✅ 为什么是 Rank #1：改动量小（~30 行净改动），收益大，无新依赖（EventEmitter 内置），不影响前端。 ✅ 风险控制：5 个副作用都有已知的消除方案，当前场景下一个都不会触发。 ✅ 给未来铺路：这个改动做好了，后面升级 WebSocket、加日志、加统计、甚至加 MCP Server 都只需要新建文件 + 一行 bus.on。
