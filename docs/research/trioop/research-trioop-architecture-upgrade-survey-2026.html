2.2 对你场景的收益——重新评估

之前我说"换框架收益 < 1ms"，但代理研究补充了新的角度：

角度之前判断更新后
API 路由延迟收益 < 1ms✅ 不变——你的 API 调用频率确实极低
SSE 推流收益 < 1ms❌ 修正——Hono 的内置 SSE helper 比 Express 手动 res.write 更可靠，自带断线重连
冷启动时间没考虑⚠️ 450ms → 120ms，开发体验有提升
代码量/维护没考虑⚠️ Express 58KB → Hono 12KB，Hono 原生 TS 类型推导更好
未来多运行时没考虑⚠️ 如果以后要跑在 Bun 或边缘，Hono 跨运行时，Express 锁死在 Node

🏆 结论修正：Express 不急着换，Hono 从"跳过"提级到"有空试试"

✅ 当前不换 — 收益确实不高，不构成紧急项

🔬 但 Hono 值得花半天试一下原型 — API 和 Express 接近，迁移一个路由试试手感，下次重构时再批量换

❌ Fastify 不推荐 — 对你场景比 Hono 重太多，收益相同，成本更高

2.3 tRPC 有必要吗？

tRPC 让前后端共享类型，调用像本地函数。但你的数据流主要是 SSE 后端→前端推送，不是前端主动调用后端 API。tRPC 的优势在这里用不上，反而多了一层打包/解包开销。

不需要。

四、Rust 的渗透：Tauri、napi-rs、边缘网关

4.0 Rust 安全性——工控合规的重要加分项

对比RustC/C++
漏洞密度（Google 2025 数据）0.2 / 百万行~1000 / 百万行
差距Rust 安全 5000 倍于 C/C++
工控合规这对 IEC 62443（工业通信网络安全标准）认证是重大优势
工业巨头西门子、博世等 25 家公司已确认在生产中使用 Rust

这意味着：如果 Trioop 未来要过工业安全认证，Rust 化的 S7 通信层将大幅降低合规成本。

4.1 napi-rs——最务实的 Rust 化方案

不需要重写整个项目。用 napi-rs（Rust 写 Node.js 原生插件），只把 S7 协议层（PDU 编解码、TCP 管理）用 Rust 写，编译成 .node 文件，Node.js 直接 import：

┌─ Node.js 后端（不改）────────────────┐ │ import { s7Connect, s7Read } from │ │ '@trioop/s7-native' │ ← 从 Rust 编译来的 .node 文件 │ Express API → s7Read() │ │ SSE push → s7Connect() │ └───────────────┬───────────────────────┘ ↓ 调用 N-API 桥 ┌───────────────┴───────────────────────┐ │ Rust napi-rs 插件（~200 行） │ │ S7 PDU 编解码 · TCP 管理 · 重连逻辑 │ │ 0 unsafe · IEC 62443 友好 · ~1ms PDU │ └───────────────────────────────────────┘

收益：Node.js 后端代码几乎不改（只改 import），协议解析性能接近纯 Rust，安全合规加分。

4.3 但 Tauri 的代价

  • nodes7/node-opcua 不能用 — 必须用 Rust 重写 S7 通信层（用 rust7 crate）
  • Express API 不能用 — 需要重写为 Rust 的 HTTP 框架（Actix/Axum）
  • Rust 学习曲线 — 从 JS 到 Rust 的跨度很大
  • 开发迭代慢 — Rust 编译时间以分钟计，Vite HMR 以毫秒计

🔬 napi-rs 插件 — 最务实路线。不改后端架构，只把 S7 协议层 Rust 化。适合未来如果要冲合规的场景

✅ 现在保持现状 — 完全够用，Rust 化是未来选项，不是现在

五、事件驱动架构：最能立刻改善代码结构的改动

这不是换框架，而是改数据流模式——性价比极高的架构改进。

5.1 现在 vs 推荐

现在（紧耦合）： setInterval(() => { const result = await plc.readOnce() ← 定时器直接调 broadcast(result) ← 直接推 SSE }, 500) 推荐（事件驱动）： setInterval → 产生 data 事件 ─→ EventBus.emit('plc:data', result) ├→ 推 SSE (互不耦合) ├→ 存 SQLite（历史趋势） └→ 检查阈值 → 报警

Node.js 自带 EventEmitter，不需要额外依赖：

import { EventEmitter } from 'events'
export const bus = new EventEmitter()

// 轮询代码（plc.ts 或 index.ts）
setInterval(async () => {
  const result = await plc.readOnce()
  bus.emit('plc:data', result)
}, 500)

// SSE handler（独立文件）
bus.on('plc:data', (data) => {
  sseClients.forEach(res => res.write(`data: ${JSON.stringify(data)}\n\n`))
})

// 未来加历史存储（独立文件，不改轮询代码）
bus.on('plc:data', (data) => {
  db.insert({ timestamp: Date.now(), values: data })
})

5.2 好处

  • 解耦 — 加新功能（报警、历史、日志）不用改轮询代码
  • 背压 — 消费者处理不过来时可以降采样/跳过
  • 测试 — 可以 mock EventBus 做单元测试
  • 改动小 — 只改数据流方式，不改任何业务逻辑

🏆 结论：推荐做。这是本报告里性价比最高的建议。

半天到一天的改动量，换来可维护性质的提升。而且不需要学习任何新框架。

十、一句话总结

🏆 当前架构（Node.js + Express + React + NodeS7）对你的场景是最优解。 ✅ 不需要改运行时（Bun/Deno） ✅ 不需要换框架（Express 够用，Hono 可以玩但不急） ✅ 不需要换桌面方案（Tauri 太折腾） ✅ 不需要换前端（React 够用） 🔥 真正值得做的三件事（按优先级）： 1. 事件驱动架构拆分 — 半天，可维护性质变 2. @autexis/nodes7 — 一行改版本号，白嫖修 bug 3. 前端时间戳去重 — 半天，减少无效渲染 🔬 远期关注：Hono.js（下一次重构时） · napi-rs（合规需求时） · Solid.js（高频推送时） · MCP Server（要对接 AI 时）
