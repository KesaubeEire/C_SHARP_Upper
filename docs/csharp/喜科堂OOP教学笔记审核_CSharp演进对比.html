🎯 2. IL / CLR / CTS 编译运行原理

✔ 笔记正确 有演进

你的笔记：

  • "IL 的作用：dotnet 平台的玩意儿都会变成 IL → 虚拟机 CLR → 机器码，两步编译"
  • "CLR 是托管代码的处理器，把一些危险操作安全化"
  • "CTS 通用类型系统，解决不同开发语言之间的数据类型差异"

📖 课程教了什么：第02节有专门讲解，课程的 App.config 里还有 supportedRuntime version="v4.0" 的 CLR 版本绑定（已随升级 .NET 10 删除）。

✅ 准确性确认：

  • ✔ 两步编译：正确。 C# 源码 → (Roslyn 编译器) → IL 中间语言 → (CLR JIT) → 机器码。这仍是 .NET 10 的核心流程。
  • ✔ CLR 托管安全：正确。 CLR 提供内存管理（GC）、类型安全、异常处理、线程管理、安全检查，防止缓冲区溢出等 C/C++ 常见问题。
  • ✔ CTS 统一类型：正确。 例如 C# 的 int 和 VB.NET 的 Integer 都映射到 System.Int32。

🔬 C# 演进 & 补充：

概念.NET Framework 时代（课程讲法）.NET 10 现状
IL C# → IL → CLR JIT → 机器码 多了 ReadyToRun (R2R)（发布时预编译，启动更快）和 Native AOT（直接编译成本地代码，无 JIT，无 IL）。
CLR 仅 Windows，单一 CLR CoreCLR（跨平台），支持 Tiered Compilation（分层编译：先用 Quick JIT 快速启动，再用 Optimizing JIT 热路径优化）。
CLS 公共语言规范 仍是规范，但如今跨语言互操作场景很少（多数人全用 C#）。仍存在但重要性下降。
CTS 通用类型系统 未变，新增 Span<T>、record、record struct 等新类型。
⚠ 笔记中的一点："虚拟机 CLR"这个说法不完全准确。CLR 不是虚拟机（不像 JVM 那样模拟硬件），它是一个运行时环境（Runtime），提供 JIT 编译 + 托管执行。JVM 解释字节码，CLR 把 IL 编译为原生机器码再执行。性能模型不同。

3.1 命名空间

✔ 笔记正确 有演进

你的笔记："命名空间是用来管理类的，类先引用后引入再使用，命名空间带点不代表有总的命名空间，他们是平级的"

📖 课程：第03节讲解，源码中所有项目都使用 namespace xiketang.com.PropertyApp { } 这种完整命名空间。

🔬 演进：

  • C# 10 文件级命名空间：在 .NET 6+ 项目中（包括你的 TEST_101），推荐使用 namespace MyProject;（文件范围命名空间），省去一层大括号缩进。课程用的是旧式 namespace xxx { } 块语法。
  • ImplicitUsings：.NET 6+ 启用后自动引入常用命名空间（System、System.Linq、System.Collections.Generic 等），无需手写大量 using。

using System.Linq;

// C# 10+ 现代写法
// csproj 里 <ImplicitUsings>enable</ImplicitUsings> + 全局 usings
namespace xiketang.com.GenericList;  // 文件级，省去一对大括号

✔ 笔记正确

// 但类的成员里仍然不能直接写执行语句 —— 这点永远不变。

3.3 类型转换三种方式

✔ 笔记正确

你的笔记："自动类型转换 / 强制类型转换会丢精度，(int) / int.Parse / Convert.ToInt32() 三种转换的适用场景"

✅ 准确性：正确。三种方式对比：

方式适用场景失败行为

4.2 属性的 C# 版本演变

🔬 课程已自演进

课程源码 Course1.cs 已展示：

// C# 2.0：标准属性（课程演示）
private int courseId = 0;
public int CourseId
{
    get { return courseId; }
    set { courseId = value; }
}

// C# 3.0：自动属性（课程演示）
public string CourseName { get; set; }

// C# 4.0：属性表达式（课程演示，说一般不用）
public int UnitPrice { get => unitPrice; set => unitPrice = value; }

// C# 6+：表达式体属性（只读）
public string FullName => $"{FirstName} {LastName}";

// C# 11+：required 修饰符（课程没有，现代推荐）
public required string CourseName { get; set; }
// 创建对象时必须初始化 required 属性：new Course { CourseName = "xxx" }
💡 现代 C# 10+ 推荐：
  • 简单数据对象用 record 类型（自动生成 Equals/GetHashCode/ToString/Deconstruct）
  • 不可变数据用 init 访问器：public string Name { get; init; } ——只能在初始化时赋值
  • 必需属性用 required：编译器强制调用方初始化，防止 null 引用问题

🎯 5. 面向对象：方法 Method

5.1 构造方法 & this 串联

✔ 笔记正确

你的笔记："构造方法可以重载，之前用 this，现在可以不用了，可以用 :this(type a, type b) 调用之前的构造方法，只能通过 new 调用"

📖 课程源码 MethodApp/Constructor/Course.cs：

// 课程教的 this 串联（仍是标准写法）
public Course(int courseId, string courseName, string type)
    : this(courseId, courseName)  // 调用上一个构造方法
{
    this.Type = type;
}
⚠ 你的笔记中"之前用 this，现在可以不用了"：你的意思可能是"之前每个构造方法各自写 this.xxx = xxx，现在可以用 :this() 串联避免重复"。但 :this() 本身就是"使用 this"——语法没变过。如果是指方法内部对成员变量的 this 引用，当成员和参数同名时仍然必须用 this区分。

5.2 析构函数（Finalizer）

✔ 笔记基本正确 有演进

你的笔记："析构函数 ~对象名(){} 对象被释放的时候执行，GC.Collect() 手动执行析构函数，不过我们不用管，CLR 会自动清理"

📖 课程源码 MethodApp/Constructor/Course.cs:50-54：

// 课程演示的析构函数
~Course()
{
    Console.WriteLine("对象被释放，析构函数被调用...");
}
// 注释也写了："这个其实是由虚拟机帮我们完成，我们没必要多管闲事！"
🔬 现代 C# 的最佳实践：
  • GC.Collect() 确实不该手动调——课程和笔记都对。
  • C# 7+ IDisposable + using 声明：对于需要释放非托管资源的对象，推荐实现 IDisposable 接口，用 using var x = new Resource(); 自动释放，不依赖 Finalizer。
  • C# 8+ IAsyncDisposable：异步资源释放用 await using var x = new AsyncResource();
  • Finalizer 的代价：有析构函数的对象需要两次 GC 才能回收（先入 Finalizer 队列），现代代码中极少使用。除非包装非托管句柄，否则不要定义 Finalizer。

5.3 静态方法

✔ 笔记正确 观点可商榷

你的笔记："静态方法是给类的，始终占内存，不宜使用过多？DeepSeek 不用考虑这个，要用 static 关键字"

✅ 准确性："始终占内存"在严格意义上是真的（静态成员在类型加载时分配，存活到 AppDomain 卸载），但对现代 PC/服务器来说内存完全不是问题。

💡 现代理解：

  • 静态方法没有性能问题（不需要实例，调用更快，不涉及虚表查找）。
  • 真正的考量是可测试性：静态方法难以 mock/替换，写单元测试不如实例方法方便。这是现代开发中更重要的考量。
  • .NET 6+ 的 static abstract 接口成员（C# 11）让静态多态成为可能，是静态方法的一个重要演进。

5.4 命名参数

✔ 笔记正确

5.5 方法重载

✔ 笔记正确

你的笔记："方法重载的意义：显示一个方法，降低类的复杂度，是多态的一种形式(比较弱那种)"

✅ 准确。重载是编译时多态（Ad-hoc Polymorphism），接口/虚方法是运行时多态。课程在 GenericList 的排序部分深入展开了运行时多态。

🔬 现代补充：C# 4+ 的可选参数（默认值）可以替代部分重载场景，减少方法数量：

// 传统：三个重载
public void Log(string msg) { ... }
public void Log(string msg, LogLevel level) { ... }
public void Log(string msg, LogLevel level, string source) { ... }

// 现代：一个方法 + 默认参数（当默认值简单时）
public void Log(string msg, LogLevel level = LogLevel.Info, string source = "") { ... }

6.3 排序：IComparable / IComparer / LINQ

✔ 笔记正确 有简化方案

你的笔记："IComparable 让对象自己知道如何排序；IComparer 让外部观察者定义排序规则。两者配合使用，可以灵活应对各种排序需求。Lambda 和 LINQ 可以更便捷/自由实现排序"

📖 课程源码 GenericList/Course.cs —— 完整教学 IComparable & IComparer：

// 课程教的 IComparable：对象自己知道如何排序
public class Course : IComparable<Course>
{
    public int CompareTo(Course other)
    {
        return other.CourseId.CompareTo(CourseId);  // 降序
    }
}
courseList.Sort();

// 课程教的 IComparer：外部定义排序规则（多态体现）
class CourseIdASC : IComparer<Course> { ... }
class CourseIdDESC : IComparer<Course> { ... }
class CourseClassASC : IComparer<Course> { ... }
courseList.Sort(new CourseIdASC());

// 课程最后演示的 LINQ（说"高级课程中用的方法，先体验"）
var list = courseList.OrderByDescending(c => c.CourseId).ToList();
💡 现代 C# 10+ 最佳实践：
IComparable/IComparer 是理解多态的好教学工具，但实际开发中 90% 的排序场景直接用 LINQ：
var sorted = list.OrderBy(c => c.CourseId).ThenBy(c => c.CourseName);
比写一堆 IComparer 类简洁得多。只有需要在多种不同排序策略间频繁切换且性能敏感时，才值得预定义 IComparer。

7.1 工具箱拖放 & 部分类

    .Where(b => b.Tag?.ToString() != "Save")
    .ToList()
    .ForEach(b => b.Click += btn_Click);
