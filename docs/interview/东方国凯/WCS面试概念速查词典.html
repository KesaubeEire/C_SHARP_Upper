一、.NET / C# 基础概念

依赖注入 DI 必会

白话解释：依赖注入就是“不要自己到处 new 对象，让框架统一创建并传给你”。

比如 Controller 要用 TaskService，你不在 Controller 里写 new TaskService()，而是在启动时注册服务，框架自动传进来。

WCS 里为什么用：PLC 连接、任务调度器、报警服务、数据库服务都要被多个模块使用。用 DI 可以统一管理生命周期，也方便测试和替换实现。

// Program.cs
builder.Services.AddSingleton<PlcService>();
builder.Services.AddScoped<TaskService>();

// Controller
public class TasksController : ControllerBase
{
    private readonly TaskService _taskService;

    public TasksController(TaskService taskService)
    {
        _taskService = taskService;
    }
}
生命周期意思WCS 例子
Singleton整个程序只有一个实例。PLC 连接管理、任务调度器、配置服务。
Scoped一次 HTTP 请求一个实例。业务服务、数据库上下文。
Transient每次用都创建新实例。轻量工具类、格式转换器。

坑：不要把数据库上下文做成 Singleton；不要在 Singleton 里直接长期持有 Scoped 服务。

面试说法：依赖注入让服务创建和生命周期由容器统一管理。WCS 里 PLC 通讯服务、报警服务、调度服务都适合注册到 DI，Controller 或后台任务只依赖接口，不直接 new 实现。

接口 Interface

白话解释：接口是一份“能力合同”。它只说你必须会什么，不关心你怎么实现。

public interface IPlcClient
{
    Task<byte[]> ReadDbAsync(int db, int start, int length);
    Task WriteDbAsync(int db, int start, byte[] data);
}

WCS 里为什么用：今天用 Sharp7，明天可能换 S7.NetPlus 或 OPC UA。业务层依赖 IPlcClient，底层实现可以替换。

面试说法：我会把 PLC 读写抽象成接口，业务层只关心读写 DB 或设备状态，不绑定具体通讯库，这样方便测试、Mock 和后续替换协议。

Task

白话解释：Task 表示一个正在执行或将来完成的工作。它不等于线程，而是“异步工作的抽象”。

WCS 里为什么用：PLC 轮询、WMS 接口调用、数据库保存、报警推送都可能耗时，不能把主线程卡住。

public async Task<DeviceStatus> GetStatusAsync()
{
    var bytes = await _plc.ReadDbAsync(1, 0, 20);
    return DecodeStatus(bytes);
}

面试说法：Task 用来表达异步操作，尤其适合 IO 等待。WCS 里大量设备通讯和接口请求都应该异步化，避免线程被等待浪费。

async / await 必会

白话解释：async 表示这个方法里可以异步等待；await 表示“等它完成，但不要傻站着占住线程”。

public async Task SaveAlarmAsync(Alarm alarm)
{
    await _repository.InsertAsync(alarm);
    await _hub.Clients.All.SendAsync("AlarmRaised", alarm);
}

坑：不要随便用 .Result 或 .Wait() 阻塞等待，可能造成死锁或线程池耗尽。

面试说法：await 会把后续逻辑挂起，等异步操作完成后继续，不会像同步等待那样占住线程。WebAPI 和设备通讯里可以提升并发能力。

CancellationToken 必会

白话解释：它是一个“停止信号”。后台任务不要被强杀，而是收到信号后自己退出。

while (!token.IsCancellationRequested)
{
    await ReadPlcOnceAsync(token);
    await Task.Delay(200, token);
}

WCS 里为什么用：停止轮询、切换 PLC、关闭程序、重启服务时，都要让后台任务安全退出。

面试说法：后台轮询必须支持 CancellationToken，否则停止监控或程序退出时可能残留任务，导致重复读写 PLC 或资源泄漏。

SemaphoreSlim / lock 必会

白话解释：它们都是“排队工具”。同一时间只允许一个人进入关键区域。

WCS 里为什么用：单个 PLC 连接通常不能让多个线程同时读写，否则可能响应错乱或连接异常。

private readonly SemaphoreSlim _plcLock = new(1, 1);

public async Task<byte[]> ReadAsync()
{
    await _plcLock.WaitAsync();
    try
    {
        return await _plc.ReadAsync();
    }
    finally
    {
        _plcLock.Release();
    }
}

面试说法：我会把同一个 PLC 连接上的读写串行化。高频采集和命令写入可以走统一队列或锁，避免并发冲突。

线程池 ThreadPool

白话解释：.NET 维护的一组可复用工作线程。你丢一个短任务进去，它找空闲线程执行，不用每次创建新线程。

WCS 里为什么用：Task.Run、WebAPI 请求处理、很多后台工作都会用线程池。

最小例子

// 把一段后台计算丢给线程池执行
await Task.Run(() =>
{
    // 例如解析一大段 PLC 导出的 DB 文件
    ParseLargeDbFile();
});
请求进入 ASP.NET Core ↓ 框架从线程池取一个工作线程 ↓ 执行 Controller / 业务代码 ↓ 请求完成，线程归还线程池

坑：不要把大量长时间阻塞操作塞进线程池，比如大量 .Wait()、同步 Socket 阻塞，否则请求会变慢。

并发、并行、异步

概念白话解释例子
并发同时处理多件事，不一定真的同时执行。WebAPI 同时接多个请求。
并行真的多个 CPU 核心同时执行。多线程同时计算大量数据。
异步等待 IO 时先让出线程，完成后继续。等待 PLC/数据库/HTTP 返回。

流程图例子

并发：一个人同时处理多个窗口 窗口 A 等 PLC 返回时，先处理窗口 B 的请求 并行：多个人真的同时干活 CPU 核心 1 解析 DB 文件，CPU 核心 2 计算报表 异步：发出请求后不傻等 发起 PLC 读取 → 释放线程 → PLC 返回 → 继续处理数据

二、WebAPI / 后端概念

ASP.NET Core

白话解释：微软的 Web 后端框架，用来写 HTTP 接口、网站、后台服务。

WCS 里为什么用：WMS/MES 要调用 WCS 接口，Vue 页面要获取任务、设备、报警数据，ASP.NET Core 就是服务端入口。

最小项目结构例子

Wcs.Api/
  Program.cs              // 启动入口，注册服务和中间件
  Controllers/
    TasksController.cs    // 任务接口
    DevicesController.cs  // 设备接口
  Services/
    TaskService.cs        // 任务业务逻辑
    PlcPollingWorker.cs   // PLC 后台轮询
  Models/
    TaskDto.cs            // 接口数据结构
Vue 看板 / WMS ↓ HTTP ASP.NET Core WebAPI ↓ 任务服务 / PLC 服务 / 数据库 ↓ 返回任务状态、设备状态、报警信息

WebAPI 必会

白话解释：WebAPI 就是“通过 HTTP 暴露出来的功能入口”。别人发请求，你返回数据或执行动作。

POST /api/tasks/inbound → WMS 下发入库任务
GET /api/devices → 前端查询设备状态

请求流程例子

WMS 发 POST /api/tasks/inbound ↓ TasksController 接收 CreateInboundTaskDto ↓ TaskService 校验托盘、物料、库位 ↓ 写入数据库，生成 WCS 任务 ↓ 后台调度器下发 PLC ↓ 返回 taskId 给 WMS

面试说法：WCS 的 WebAPI 主要用于接收 WMS 任务、回传任务状态、提供设备状态和报警数据。接口要考虑幂等、日志、异常和权限。

HTTP

白话解释：浏览器、前端、系统之间通信的一种协议。常见动作有 GET、POST、PUT、DELETE。

方法含义WCS 例子
GET查询数据。查询任务状态。
POST创建或触发动作。下发入库任务。
PUT整体更新。修改设备配置。
DELETE删除。删除测试任务。

原始 HTTP 请求长什么样

POST /api/tasks/inbound HTTP/1.1
Host: wcs.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{
  "palletCode": "P20260709001",
  "materialCode": "M001",
  "targetLocation": "A01-02-03"
}

Controller

白话解释：Controller 是接口的入口类。URL 匹配到某个方法后，就由这个方法处理请求。

[ApiController]
[Route("api/devices")]
public class DevicesController : ControllerBase
{
    [HttpGet]
    public IActionResult GetDevices()
    {
        return Ok(_deviceService.GetAll());
    }
}

DTO

白话解释：DTO 是接口收发的数据包。它只服务于接口，不一定等于数据库表。

public class DeviceStatusDto
{
    public string DeviceCode { get; set; } = "";
    public string Status { get; set; } = "";
    public int ErrorCode { get; set; }
}

面试说法：接口层我会用 DTO 隔离外部协议和内部数据库模型，避免数据库结构变化直接影响 WMS 或前端。

中间件 Middleware 必会

白话解释：中间件是 HTTP 请求经过的一条流水线。每个中间件处理一件事，比如日志、异常、鉴权、路由。

请求 → 异常处理 → 日志 → 鉴权 → 路由 → Controller → 响应
app.UseExceptionHandler();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

WCS 里为什么用：所有接口都需要统一日志、异常返回、权限控制。否则每个 Controller 都手写一遍，容易乱。

它到底“中”在哪里

浏览器、WMS 或 Vue 前端访问后端时，请求不会直接冲进 Controller。它会先经过一串处理环节，这串环节就叫中间件管道。每个中间件可以在请求进入 Controller 前做事，也可以在 Controller 返回后做事。

客户端请求 → 中间件 A → 中间件 B → 中间件 C → Controller → 中间件 C → 中间件 B → 中间件 A → 客户端响应

用保安/前台类比

Controller 像办公室里的业务人员，中间件像大楼门口的一层层关卡：

  • 门口保安：检查有没有证件，对应认证鉴权。
  • 前台登记：记录谁来过、几点来的，对应访问日志。
  • 安检：发现危险请求直接拦截，对应限流、黑名单、参数检查。
  • 事故处理员：业务人员出错时统一处理，对应全局异常处理。

中间件一般有什么作用

作用白话解释WCS 例子
异常处理代码出错时统一返回错误格式。WMS 调接口失败时返回错误码和错误消息，而不是一堆堆栈。
请求日志记录谁在什么时候调用了哪个接口。记录 WMS 下发任务、取消任务、人工确认报警的请求。
认证 Authentication判断“你是谁”。根据 JWT token 识别当前用户或外部系统。
授权 Authorization判断“你有没有权限做这件事”。操作员不能修改 PLC 配置，工程师可以。
跨域 CORS允许指定前端域名访问后端接口。Vue 开发服务器访问 ASP.NET Core 后端。
静态文件直接返回 HTML/CSS/JS/图片。部署时后端顺带托管前端打包文件。
路由把 URL 分发到对应 Controller。/api/tasks/T001 进入任务查询接口。
限流限制接口访问频率。防止外部系统高频重复查询压垮 WCS。
请求体解析把 JSON 请求体转成 C# 对象。把 WMS 的入库任务 JSON 转成 DTO。
响应压缩减少传输数据大小。设备状态列表很大时降低网络传输量。

常见中间件顺序

中间件顺序很重要。放错顺序，可能导致鉴权不生效、异常抓不到、跨域失败。

var app = builder.Build();

// 1. 最外层：异常处理，尽量放前面，方便兜住后面错误
app.UseExceptionHandler();

// 2. HTTPS、静态文件、跨域等基础能力
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseCors("DefaultCors");

// 3. 认证和授权：先认证你是谁，再判断你能做什么
app.UseAuthentication();
app.UseAuthorization();

// 4. 最后映射 Controller
app.MapControllers();

app.Run();

一个最小自定义中间件

下面这个中间件会记录每个请求耗时。它先记开始时间，再调用 next() 让请求继续往后走，等后面的 Controller 执行完，再记录耗时。

app.Use(async (context, next) =>
{
    var start = DateTime.UtcNow;

    await next(); // 放行给下一个中间件或 Controller

    var elapsed = DateTime.UtcNow - start;
    Console.WriteLine($"{context.Request.Path} took {elapsed.TotalMilliseconds}ms");
});

关键点：await next() 前面的代码是在 Controller 之前执行，后面的代码是在 Controller 之后执行。如果不调用 next()，请求就会被这个中间件拦住，不再进入后面的 Controller。

WCS 里最值得做的中间件

  • 统一异常中间件：所有接口统一返回 { code, message, traceId }，方便 WMS/MES 联调。
  • 请求日志中间件：记录任务下发、取消、确认报警、修改配置等关键操作。
  • 鉴权中间件：区分管理员、工程师、操作员、外部系统调用方。
  • TraceId 中间件：给每个请求生成唯一 ID，日志排查时能串起来。
  • 限流中间件：防止外部系统异常重试，把 WCS 接口打爆。

可能被问到的面试题

面试问题推荐回答
中间件是什么？ 中间件是 ASP.NET Core 处理 HTTP 请求的管道组件。请求进入 Controller 前会经过一系列中间件，响应返回时也会反向经过它们。
中间件有什么作用？ 常见作用包括异常处理、日志、认证、授权、跨域、静态文件、路由、限流、响应压缩等。
中间件顺序重要吗？ 重要。比如认证要在授权前面；异常处理中间件要尽量靠前；CORS 要在接口映射前配置，否则可能不生效。
UseAuthentication 和 UseAuthorization 有什么区别？ Authentication 判断你是谁，Authorization 判断你有没有权限。顺序通常是先认证再授权。
如果中间件里不调用 next() 会怎样？ 请求会被短路，后面的中间件和 Controller 都不会执行。可以用来拦截非法请求或直接返回缓存响应。
WCS 项目你会用中间件做什么？ 我会做统一异常、请求日志、TraceId、认证授权和限流。任务下发、取消、报警确认这类关键接口必须可追踪。

面试说法：中间件是 ASP.NET Core 的请求处理管道。WCS 接口会统一做异常处理、访问日志、认证授权和路由分发。

路由 Route

白话解释：路由就是“URL 和代码方法的对应关系”。

[Route("api/tasks")]
public class TasksController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult GetTask(string id) { ... }
}

请求 GET /api/tasks/T001 就会进入 GetTask("T001")。

JWT

白话解释：JWT 是一种登录令牌。用户登录后，服务端发一个 token；后续请求带着 token，服务端验证你是谁。

WCS 里为什么用：不同角色权限不同：操作员只能看和确认报警，工程师可以改配置，管理员可以管理用户。

调用接口时怎么带 JWT

GET /api/alarms HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI...
用户登录 ↓ 后端校验账号密码 ↓ 后端签发 JWT ↓ 前端保存 token ↓ 后续请求在 Authorization 头里带 token ↓ 后端认证中间件解析 token，识别用户身份

坑：JWT 不是加密保险箱，敏感信息不要直接放进去；要设置过期时间。

Swagger / OpenAPI

白话解释：自动生成接口文档和调试页面。你写好 WebAPI 后，可以在网页上看到有哪些接口、参数是什么、返回什么。

WCS 里为什么用：和 WMS/MES/第三方系统对接时，接口文档非常重要。Swagger 能帮助联调。

配置例子

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();
app.UseSwagger();
app.UseSwaggerUI();
开发人员写 Controller ↓ Swagger 扫描接口和 DTO ↓ 生成网页文档 ↓ WMS/MES 对接人员按文档联调

BackgroundService 必会

白话解释：ASP.NET Core 里的后台常驻任务。WebAPI 接口负责“别人来找我”，BackgroundService 负责“我自己一直干活”。

WCS 里为什么用：PLC 轮询、任务调度、心跳检查、报警扫描都适合后台服务。

public class PlcPollingWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken token)
    {
        while (!token.IsCancellationRequested)
        {
            await _plc.ReadStatusAsync(token);
            await Task.Delay(200, token);
        }
    }
}

面试说法：WCS 后端不仅提供 WebAPI，还需要后台服务持续轮询 PLC、扫描任务状态和报警。BackgroundService 适合承载这些长期运行任务。

SignalR

白话解释：SignalR 是 .NET 的实时推送技术。普通 HTTP 是前端问一次后端答一次；SignalR 可以让后端主动推消息给前端。

WCS 里为什么用：设备状态、任务进度、报警变化需要实时展示。如果前端一直轮询会浪费资源，SignalR 更合适。

推送例子

public class DeviceHub : Hub { }

// 后台服务读到设备状态变化后推送给前端
await _hubContext.Clients.All.SendAsync(
    "DeviceStatusChanged",
    new { deviceCode = "Stacker01", status = "Fault" });
PLC 状态变化 ↓ 后台轮询服务检测到变化 ↓ SignalR Hub 推送 DeviceStatusChanged ↓ Vue 看板立即更新设备状态

面试说法：设备状态和报警适合用 SignalR 推送到 Vue 看板，避免前端高频刷新，提高实时性。

幂等 Idempotency 重要

白话解释：同一个请求执行一次和执行多次，结果应该一样，不应该造成重复副作用。

WCS 里为什么用：WMS 可能因为网络超时重复下发同一个任务。WCS 必须识别外部任务号，不能重复创建、重复下发 PLC。

代码思路例子

public async Task<TaskResult> CreateInboundTaskAsync(CreateTaskDto dto)
{
    var existing = await _repository.FindByExternalTaskIdAsync(dto.ExternalTaskId);
    if (existing != null)
    {
        return TaskResult.FromExisting(existing);
    }

    var task = CreateNewTask(dto);
    await _repository.InsertAsync(task);
    return TaskResult.FromNew(task);
}
WMS 第一次下发 ExternalTaskId = WMS001 ↓ WCS 查不到 → 创建任务 T001 WMS 超时后重复下发 ExternalTaskId = WMS001 ↓ WCS 查到已有任务 T001 ↓ 返回 T001 当前状态，不重复创建

面试说法：任务下发接口要按外部任务号做幂等。重复请求时返回已有任务状态，而不是再创建一条任务。

全局异常处理

白话解释：程序出错时，不要把一堆堆栈直接丢给调用方，而是统一记录日志、返回标准错误格式。

WCS 里为什么用：现场联调时，错误必须可追踪。调用方也需要稳定错误码，不想看到乱码堆栈。

返回格式例子

{
  "code": "PLC_TIMEOUT",

四、PLC / 工控通讯概念

PLC 必会

白话解释：PLC 是工业现场的控制器，可以理解成设备的大脑。它负责控制电机、气缸、传感器、输送线、堆垛机动作。

WCS 软件 → PLC → 电机/传感器/伺服/变频器

现场控制流程图

传感器检测到托盘到位 ↓ 输入信号进入 PLC 的 I 区 PLC 程序判断条件满足 ↓ 输出信号写入 Q 区 变频器/接触器/伺服驱动动作 ↓ 输送线或堆垛机执行动作 ↓ PLC 把状态写入 DB 状态区 ↓ WCS 读取状态并更新任务

上位机

白话解释：上位机是运行在 PC 上的软件，用来监控设备、采集数据、下发参数、显示报警。

和 WCS 的关系：WCS 可以看作更偏业务和调度的上位系统；普通上位机更偏单机设备监控。

上位机数据流例子

PLC / 仪表 / 相机 ↓ S7 / Modbus / SDK 上位机采集服务 ↓ 界面显示实时状态 ↓ 报警、趋势、历史记录、参数下发

S7 协议

白话解释：西门子 PLC 常用的通讯协议。S7-1200/1500 通常通过以太网的 ISO-on-TCP 通讯，默认端口 102。

连接和读写流程

WCS 配置 PLC IP、Rack、Slot ↓ TCP 连接 PLC:102 ↓ S7 ISO 握手 / PDU 协商 ↓ DBRead / ReadArea 读取状态 ↓ DBWrite / WriteArea 写入命令 ↓ 断线后重连并恢复轮询

面试说法：S7 通讯里我重点关注连接参数、DB/I/Q/M 区读写、数据类型解析、断线重连和读写串行化。

Rack / Slot

白话解释：连接西门子 PLC 时需要的机架号和槽号。S7-1200/1500 常见配置是 Rack 0、Slot 1，但要以实际 PLC 配置为准。

连接参数例子

PLC IP   : 192.168.1.10
Port     : 102
Rack     : 0
Slot     : 1
Protocol : S7 ISO-on-TCP

I / Q / M / DB 区 必会

区域含义例子
I输入区。传感器到位、光电信号、按钮。
Q输出区。启动电机、控制指示灯。
M中间存储区。PLC 内部标志位、临时状态。
DB数据块。任务号、命令码、目标库位、报警码。

地址例子

I0.0       // 输入区第 0 字节第 0 位，例如光电到位
Q0.1       // 输出区第 0 字节第 1 位，例如电机启动
M10.0      // 中间区第 10 字节第 0 位，例如内部状态
DB1.DBW0   // DB1 第 0 字节开始的 WORD/INT
DB1.DBD4   // DB1 第 4 字节开始的 DINT/REAL

DB 命令区 / 状态区

白话解释：WCS 和 PLC 约定一块 DB，WCS 写命令，PLC 写状态。

字段谁写用途
TaskIdWCS任务号，防重复。
CommandCodeWCS动作码，比如入库/出库/取货/放货。
CommandTriggerWCS触发位，表示新命令。
CommandAckPLC确认收到命令。
DonePLC动作完成。
ErrorCodePLC设备故障码。

WCS 和 PLC 握手流程

WCS 写 TaskId / CommandCode / TargetLocation ↓ WCS 置位 CommandTrigger = true ↓ PLC 看到触发位，复制命令并置位 CommandAck = true ↓ WCS 看到 Ack，清除 CommandTrigger ↓ PLC 执行动作 ↓ PLC 置位 Done 或写 ErrorCode ↓ WCS 更新任务状态并回传 WMS

BOOL / INT / DINT / REAL

白话解释：PLC 数据类型。

类型含义字节例子
BOOL真假值。1 bit到位信号、触发位。
INT16 位整数。2状态码。
DINT32 位整数。4任务号、计数。
REAL浮点数。4速度、重量、温度。

DB 字节布局例子

DB1.DBB0       BYTE   设备状态码
DB1.DBX1.0     BOOL   命令触发位
DB1.DBX1.1     BOOL   命令确认位
DB1.DBW2       INT    错误码
DB1.DBD4       DINT   任务号
DB1.DBD8       REAL   当前重量

C# 和西门子常见数据类型字节数对比 必会

先记结论：C# 和西门子的类型名字有些相似，但不能直接等同。尤其是 bool / BOOL、char / CHAR、字符串、时间类型、字节序，都是面试和现场调试容易出错的点。

C# 常见类型大小

C# 类型字节数说明大致对应 PLC 类型

byte10 到 255。BYTE / USINT

最容易混淆的点

  • C# bool vs PLC BOOL：C# 通常按 1 字节理解；PLC BOOL 是 1 bit，8 个 BOOL 可以挤在 1 个字节里。
  • C# char vs PLC CHAR：C# char 是 2 字节 UTF-16；PLC CHAR 通常是 1 字节。
  • C# string vs PLC STRING[n]：C# 字符串是引用类型且长度不固定；PLC 字符串有固定最大长度，前两个字节保存最大长度和当前长度。
  • 时间类型：不要把 PLC TIME 当 REAL，它通常是 4 字节毫秒数，更适合转成 TimeSpan。
  • 字节序：C# 在 Windows/x86/x64 上通常小端；西门子 S7 多字节数值通常大端。读 INT、DINT、REAL 时要转换。
  • 优化 DB：S7-1200/1500 如果 DB 开了优化访问，绝对偏移可能不稳定；上位机按地址读写时通常要使用非优化 DB 或明确符号访问方案。

面试推荐说法

“C# 类型和 PLC 类型不能只看名字对应。比如 C# bool 通常按字节处理，但西门子 BOOL 是 bit；C# char 是 2 字节，而 PLC CHAR 是 1 字节；PLC STRING[n] 前两个字节是最大长度和当前长度。S7 多字节数据通常按大端存储，所以读 INT、DINT、REAL 时要做字节序转换。我会把这些转换集中封装，避免业务代码里到处手写解析。”

字节序 Endianness

白话解释：多字节数字在内存里先放高位还是低位。西门子 S7 多字节数据通常是大端，PC 常见是小端，所以转换时要注意。

DINT 字节序示意

数值：0x12 34 56 78 S7 大端存储： 地址 +0 = 0x12 地址 +1 = 0x34 地址 +2 = 0x56 地址 +3 = 0x78 C# BitConverter 在常见 Windows PC 上通常按小端解释： 需要调整字节顺序后再转 int / float

面试说法：S7 读 REAL、DINT、INT 时要注意大端字节序，BOOL 还要处理 byte.bit 偏移。我会把解码逻辑集中封装，避免页面里重复转换。

轮询 Polling

白话解释：程序定时去问设备：“你现在什么状态？”

WCS 里为什么用：PLC 通常不会主动把所有状态推给 WCS，所以 WCS 要定时读取状态区。

坑：轮询太快会压垮 PLC 或网络；太慢状态不实时。要按高频/低频分层。

轮询循环例子

每 200ms： 1. 读取 I/Q/M 快速状态 2. 读取一部分 DB 变量 3. 解码 BOOL / INT / REAL 4. 更新内存缓存 5. 触发 UI / 报警 / 任务状态更新 6. 如果失败，记录错误并退避

心跳 Heartbeat

白话解释：双方定时发一个变化的信号，证明“我还活着”。

WCS 每秒翻转 Heartbeat；PLC 如果 5 秒没看到变化，就认为通讯异常。

心跳流程

WCS 每 1 秒写 Heartbeat = 0/1 翻转 ↓ PLC 检测 Heartbeat 是否持续变化 ↓ PLC 写 PlcAliveCounter 递增 ↓ WCS 检测 PlcAliveCounter 是否持续变化 ↓ 任一方向超时 → 报警 + 停止下发新任务

OPC UA

白话解释：一种工业通讯标准。相比直接 S7 读地址，OPC UA 更像“按变量名订阅数据”。

WCS 里为什么用：跨品牌、标准化、订阅推送更方便，但实时控制场景可能仍用 S7/Modbus/厂家协议。

订阅流程图

OPC UA Client ↓ 连接 OPC UA Server（PLC 或网关） ↓ 浏览节点 选择变量 ns=2;s=Device.Stacker.Status ↓ 订阅 变量变化时 Server 主动推送给 Client

Modbus RTU / TCP

白话解释：Modbus 是很常见的工业协议。RTU 走串口，TCP 走以太网。

类型介质特点
Modbus RTURS485/串口有 CRC 校验，速度相对慢。
Modbus TCP以太网有 MBAP 头，通常端口 502。

读保持寄存器例子

// 功能码 03：Read Holding Registers
站号: 1
功能码: 03
起始地址: 0
数量: 10

请求含义：读取 1 号设备从 0 开始的 10 个保持寄存器

CRC

白话解释：CRC 是校验码，用来判断一帧串口数据传输过程中有没有出错。

Modbus RTU 里为什么用：主站收到响应后会计算 CRC，和帧尾 CRC 比较，不一致就说明数据可能坏了。

RTU 帧结构

[站号][功能码][数据...][CRC低字节][CRC高字节] 接收方： 1. 取出前面的站号 / 功能码 / 数据 2. 重新计算 CRC 3. 和帧尾 CRC 比较 4. 不一致就丢弃这一帧

Profinet

白话解释：西门子常用的工业以太网现场总线，用于 PLC、IO、伺服、变频器之间实时通讯。

WCS 通常不直接控制 Profinet 设备，而是通过 PLC 间接获取状态和下发命令。

典型关系

WCS ↓ S7 / OPC UA PLC ↓ Profinet 远程 IO / V90 伺服 / G120 变频器 / 触摸屏

伺服 / 变频器

概念白话解释例子
伺服高精度控制位置、速度、扭矩。堆垛机定位、机械轴运动。
变频器控制普通电机速度。输送线电机调速。

控制链路例子

WCS 下发目标库位 ↓ PLC 判断动作条件并发送运动命令 ↓ 伺服驱动控制堆垛机定位 ↓ 变频器控制输送线速度 ↓ 传感器反馈到位信号给 PLC ↓ PLC 把完成状态写给 WCS

五、WCS / 仓储业务概念

WMS

白话解释：仓库管理系统，管库存、订单、库位策略、批次、账务。

WMS 视角例子

销售订单需要出库 10 箱物料 A ↓ WMS 查询库存和批次 ↓ WMS 选择库位 A01-02-03 的托盘 ↓ WMS 下发出库任务给 WCS ↓ WMS 等待 WCS 回传完成结果 ↓ WMS 扣减库存并更新账务

WCS 必会

白话解释：仓库控制系统，管设备执行。它把 WMS 的业务任务拆成输送线、提升机、堆垛机、AGV/RGV、PLC 能执行的动作。

WMS：我要出 A 物料 → WCS：让堆垛机去 A01 取托盘，再送到出库口

WCS 拆任务例子

WMS 出库任务：托盘 P001 从 A01 到 出库口 1 ↓ WCS 生成设备子任务： 1. 输送线入口准备 2. 堆垛机移动到 A01 3. 堆垛机取货 4. 堆垛机放到输送线 5. 输送线送到出库口 1 6. 扫码复核并回传 WMS

面试说法：WMS 管业务和库存，WCS 管设备执行和调度，PLC 管具体动作。WCS 是业务系统和现场设备之间的桥。

MES / ERP

MES：制造执行系统，关注生产过程、工单、工序、产线执行。

ERP：企业资源计划系统，关注采购、销售、财务、库存总账等企业管理。

WCS 可能需要和 WMS/MES/ERP 中的一个或多个系统对接。

系统关系例子

ERP：采购/销售/财务计划 ↓ MES：生产工单、产线投料需求 ↓ WMS：库存、批次、库位策略 ↓ WCS：调度设备搬运物料 ↓ PLC：执行具体动作

立体库

白话解释：高层货架 + 堆垛机/穿梭车 + 输送线 + 软件系统组成的自动化仓库。

组成结构图

自动化立体库 ├─ 货架 / 库位 ├─ 堆垛机 / 穿梭车 ├─ 输送线 / 提升机 ├─ 扫码 / 称重 / 外形检测 ├─ PLC / 电控系统 └─ WMS / WCS 软件系统

堆垛机 / 提升机 / 输送线

设备作用
堆垛机在巷道里横向/纵向移动，把货物放入或取出货架库位。
提升机把托盘或料箱在不同高度之间搬运。
输送线用滚筒、皮带、链条把货物从一个点输送到另一个点。

一次入库里的设备协作

托盘到入库口 ↓ 输送线把托盘送到提升机 ↓ 提升机把托盘送到目标层 ↓ 堆垛机进入巷道并取货 ↓ 堆垛机把托盘放入目标库位 ↓ PLC 返回完成信号给 WCS

入库 / 出库 / 移库 / 盘点

业务白话解释
入库货物进入仓库，系统分配库位，设备搬到目标位置。
出库根据订单把货物从库位取出，送到出库口。
移库把货物从一个库位移动到另一个库位。
盘点核对系统库存和实际库存是否一致。

四类业务怎么流转

入库：入口扫码 → 分配库位 → 设备搬运 → 入库完成 出库：订单需求 → 锁定库存 → 设备取货 → 出库复核 移库：源库位 → 目标库位 → 搬运完成 → 更新库存位置 盘点：系统库位 → 现场核对 → 差异确认 → 更新库存

任务状态机 必会

白话解释：任务从开始到结束要经历一组明确状态，不能靠几个乱七八糟的 bool 判断。

Created → Checked → Dispatched → Running → Completed
Running → Failed → ManualHandling → Retry / Cancel

状态流转例子

Created 已收到 WMS 任务 ↓ Checked 校验托盘、库位、设备状态通过 ↓ Dispatched 已写入 PLC 命令区 ↓ Running PLC/设备正在执行 ↓ Completed PLC 返回完成，WCS 回传 WMS 异常分支： Running → Failed → ManualHandling → Retry / Cancel

面试说法：WCS 任务必须有状态机并落库。系统重启后能恢复未完成任务，异常后能人工干预、重试或取消。

断点续传 / 断点恢复

白话解释：系统或设备中断后，能知道任务执行到哪一步，并从合理位置继续或人工处理。

WCS 里为什么重要：货物搬到一半不能简单重发任务，否则可能撞车、重复搬运或库存错乱。

恢复流程例子

WCS 服务重启 ↓ 从数据库读取未完成任务 ↓ 读取 PLC 当前任务号、设备位置、完成位、错误码 ↓ 比对数据库任务和 PLC 状态 ↓ 判断：继续执行 / 重试 / 取消 / 人工接管 ↓ 写操作日志并恢复调度

人工干预

白话解释：自动流程处理不了时，让操作员或工程师确认下一步。

比如条码不符、库位占用、设备故障、托盘歪斜，都可能需要人工选择“重试、取消、改库位、强制完成”。

人工干预流程

系统发现异常：条码不一致 ↓ 任务进入 ManualHandling ↓ 报警弹窗 + 记录日志 ↓ 操作员确认实际托盘 ↓ 选择：退回 / 放行 / 改任务 / 取消 ↓ WCS 按选择恢复任务状态

报警死区 / OnDelay / OffDelay

概念白话解释
死区数值在阈值附近抖动时，不要反复报警和恢复。
OnDelay异常持续一段时间才报警，避免瞬时毛刺。
OffDelay恢复持续一段时间才清除报警，避免刚恢复又故障。

温度报警例子

规则：温度 > 80℃ 报警，死区 2℃，OnDelay 3 秒，OffDelay 5 秒 触发： 温度连续 3 秒 > 80℃ → 产生报警 恢复： 报警后温度需要降到 78℃ 以下，并持续 5 秒 → 清除报警 好处： 温度在 79.9℃ 和 80.1℃ 之间抖动时，不会疯狂报警/恢复

六、WPF / 上位机概念

WPF

白话解释：微软的 Windows 桌面 UI 框架，适合做上位机、监控软件、配置工具。

上位机页面例子

WPF 主窗口 ├─ PLC 连接面板 ├─ I/Q/M 状态监控 ├─ DB 变量表格 ├─ 趋势曲线 ├─ 报警列表 └─ 配方参数页面

XAML

白话解释：WPF 用来描述界面的 XML 语言。按钮、表格、布局、绑定都可以写在 XAML 里。

XAML 最小例子

<StackPanel>
  <TextBlock Text="{Binding PlcStatus}" />
  <Button Content="连接 PLC"
          Command="{Binding ConnectCommand}" />
</StackPanel>

MVVM

白话解释：一种 WPF 常用架构，把界面、状态和业务分开。

层职责
Model数据模型，比如报警、设备、任务。
View界面 XAML。
ViewModel给界面提供数据和命令。

MVVM 数据流

View(XAML) ↓ Binding / Command ViewModel ↓ 调用 Service（PLC、报警、配方） ↓ Model（设备状态、报警项、任务数据）

面试说法：MVVM 可以减少界面代码和业务逻辑耦合，设备状态、报警列表、命令按钮都可以通过绑定和命令驱动。

数据绑定 Binding

白话解释：把界面元素和 ViewModel 属性连起来。属性变了，界面跟着变。

绑定例子

// ViewModel
public string PlcStatus { get; set; } = "未连接";

// XAML
<TextBlock Text="{Binding PlcStatus}" />

ICommand / RelayCommand

白话解释：按钮点击后执行 ViewModel 里的命令，而不是直接在界面代码里写业务。

命令例子

[RelayCommand]
private async Task ConnectAsync()
{
    await _plcService.ConnectAsync();
}
用户点击“连接 PLC” ↓ Button 触发 ConnectCommand ↓ ViewModel 调用 PlcService ↓ 连接结果更新到界面

Dispatcher

白话解释：WPF UI 只能在 UI 线程更新。后台线程读到 PLC 数据后，要通过 Dispatcher 切回 UI 线程更新界面。

代码例子

Application.Current.Dispatcher.Invoke(() =>
{
    AlarmItems.Add(newAlarm);
});

坑：后台线程直接改 ObservableCollection 可能报错，因为它属于 UI 线程。

七、数据库 / 持久化概念

数据库持久化

白话解释：把数据保存到硬盘里的数据库或文件，程序重启后还能找回来。

WCS 里为什么用：任务、报警、操作日志、库存变化不能只放内存，否则程序崩了就丢。

持久化流程

WMS 下发任务 ↓ WCS 写入数据库：TaskId、状态、库位、托盘号 ↓ WCS 下发 PLC ↓ PLC 返回完成 ↓ WCS 更新数据库状态为 Completed ↓ 系统重启后仍能查询任务历史

事务 Transaction

白话解释：一组数据库操作要么全部成功，要么全部失败。

创建出库任务 + 锁定库存 + 写任务日志：三件事要一起成功。

事务代码例子

using var tx = await db.Database.BeginTransactionAsync();

CreateOutboundTask(task);
LockInventory(location);
WriteOperationLog(task.Id, "Created");

await db.SaveChangesAsync();
await tx.CommitAsync();

EF Core

白话解释：.NET 的 ORM 框架，可以用 C# 对象操作数据库，少写 SQL。

查询例子

var runningTasks = await db.Tasks
    .Where(t => t.Status == TaskStatus.Running)
    .OrderBy(t => t.CreatedAt)
    .ToListAsync();

Dapper

白话解释：轻量 ORM。你自己写 SQL，Dapper 帮你把查询结果转成 C# 对象。性能好、可控。

查询例子

var tasks = await connection.QueryAsync<TaskRecord>(
    "select * from WcsTask where Status = @Status",
    new { Status = "Running" });

日志 Logging

白话解释：记录系统发生了什么。现场问题复盘时，日志比口头描述可靠。

WCS 至少要记录：接口请求、任务状态变化、PLC 读写异常、报警产生/确认/恢复、人工操作。

日志例子

logger.LogInformation(
    "Task {TaskId} dispatched to PLC. Device={DeviceCode}, Target={Target}",
    task.Id,
    "Stacker01",
    task.TargetLocation);
现场说“任务没执行” ↓ 查接口日志：WMS 是否下发 ↓ 查任务日志：WCS 是否创建任务 ↓ 查 PLC 日志：命令是否写入 ↓ 查报警日志：设备是否故障 ↓ 定位责任点

八、面试速记：概念串起来讲

1. 后端架构怎么说

“我理解 WCS 后端通常由 WebAPI、后台调度服务、设备通讯服务、数据库和实时推送组成。WebAPI 负责接 WMS/MES 任务和给前端提供数据；BackgroundService 负责 PLC 轮询、任务调度和报警扫描；设备通讯服务通过 S7/Modbus/OPC UA 读写设备；数据库持久化任务、报警和日志；SignalR 推送实时状态给前端。”

2. 依赖注入和中间件怎么说

“依赖注入负责服务创建和生命周期管理，比如 PLC 服务、任务服务、报警服务都注册到容器里，Controller 通过构造函数拿到依赖。中间件是 HTTP 请求管道，用来统一处理异常、日志、认证授权和路由，这样接口层更干净。”

3. PLC 通讯怎么说

“S7 通讯主要读写 I/Q/M/DB 区。WCS 和 PLC 通常约定 DB 命令区和状态区：WCS 写任务号、命令码、目标地址和触发位；PLC 写确认位、完成位、设备状态和错误码。读写要串行化，数据要注意字节序，轮询要合并连续地址并处理断线重连。”

4. WCS 业务怎么说

“WMS 管库存和业务策略，WCS 管设备执行。比如入库任务，WCS 接到 WMS 指令后校验托盘、物料、库位和设备状态，再拆成输送线、提升机、堆垛机动作，下发 PLC，轮询执行状态，完成后回传 WMS。异常时进入报警和人工干预流程。”

5. 如果问你不会怎么办

“这个点我没有在真实项目里完整落地过，但我的理解是……我会先明确接口协议和状态机，再保证任务落库、设备通讯可追踪、异常可恢复。具体实现上我可以结合项目现有框架快速补齐。”
