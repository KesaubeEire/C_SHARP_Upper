第一章

ASP.NET Core WebAPI 入门

JD 明确要求"熟练掌握 ASP.NET Core WebApi"，而你的项目经验偏 WPF 和 Node.js。这一章让你快速掌握 WebAPI 的核心概念，面试时能讲清楚。

定位：WCS 的 WebAPI 用来做什么？——接 WMS/MES/ERP 的任务指令（入库/出库/移库），对外暴露设备状态接口，前端 Vue 页面通过它展示数据和控制设备。

1.1 项目结构长什么样

一个 ASP.NET Core WebAPI 项目典型的文件结构：

MyWcsApi/
├── Controllers/          ← 接口入口（路由在这里）
│   └── TaskController.cs
├── Services/              ← 业务逻辑层
│   └── WcsTaskService.cs
├── Models/                ← 数据模型（DTO）
│   └── TaskDto.cs
├── Program.cs             ← 启动文件（DI注册、中间件配置）
├── appsettings.json       ← 配置文件（数据库连接串等）

对比你熟悉的 WPF 项目：Program.cs 相当于 App.xaml.cs（DI Host 配置），Controllers 相当于 Views（入口），Services 没变，还叫 Services。

1.2 最简 API 长什么样

先看一个最简的 Controller：

using Microsoft.AspNetCore.Mvc;

/// 这个 [ApiController] 是固定写法，表示这是一个 API 控制器
/// [Route] 定义了访问路径：/api/tasks
[ApiController]
[Route("api/[controller]")]
public class TaskController : ControllerBase
{
    /// GET /api/tasks  — 获取任务列表
    [HttpGet]
    public IActionResult GetTasks()
    {
        return Ok(new[] { "任务1", "任务2" });
    }

    /// GET /api/tasks/5  — 获取单个任务
    [HttpGet("{id}")]
    public IActionResult GetTask(int id)
    {
        return Ok($"任务 {id}");
    }

    /// POST /api/tasks  — 创建新任务
    [HttpPost]
    public IActionResult CreateTask([FromBody] TaskDto dto)
    {
        // [FromBody] 表示从请求的 JSON body 读取参数
        return Created($"/api/tasks/{dto.Id}", dto);
    }
}
面试常问：Controller 的 Route 和 HTTP 方法属性谁先匹配？回答：[controller] 是占位符（类名去掉 Controller），{id} 是路由参数，ASP.NET Core 按最具体匹配。
常用 HTTP 方法对照
[HttpGet]     → 查（读数据）
[HttpPost]    → 增（创建新数据）
[HttpPut]     → 改（全量更新）
[HttpPatch]   → 改（部分更新）
[HttpDelete]  → 删（删除数据）

// 每种方法对应一个状态码约定：
Ok(result)     → 200    GET 成功
Created(...)   → 201    POST 创建成功
NoContent()    → 204    删除成功
BadRequest()   → 400    客户端传错参数
NotFound()     → 404    资源不存在

1.3 DTO（数据传输对象）

DTO 是你定义的在 API 之间传递的数据结构。不要直接把数据库模型暴露出去。

public class TaskDto
{
    public int Id { get; set; }
    public string TaskType { get; set; }   // 入库/出库/移库
    public string Source { get; set; }     // 源位置（站台/货位）
    public string Target { get; set; }     // 目标位置
    public int Priority { get; set; }     // 优先级
}

WCS 的典型 DTO：WMS 下发任务时，JSON body 可能是：

{
  "taskType": "入库",
  "palletId": "P20260708001",
  "source": "入库口1",
  "target": "A01-03-05"
}

1.4 依赖注入（DI）

你已经熟悉 WPF 里的 DI（AddSingleton），ASP.NET Core 完全一样的概念：

// Program.cs — 注册服务
builder.Services.AddSingleton<IWcsTaskService, WcsTaskService>();
builder.Services.AddScoped<IPlcService, S7PlcService>();
builder.Services.AddHttpClient();  // 用于调用外部 API

// Controller 里通过构造函数注入
[ApiController]
[Route("api/tasks")]
public class TaskController : ControllerBase
{
    private readonly IWcsTaskService _taskService;

    public TaskController(IWcsTaskService taskService)
    {
        _taskService = taskService;  // 不用 new，DI 容器自动注入
    }
}
和 WPF 完全一样：你的 App.xaml.cs 用 AddSingleton 注册 S7Service，这边用同样的方式注册服务。面试时可以说"我熟悉 DI 模式，WPF 项目一直用"。

1.5 Middleware（中间件）

Middleware 是 ASP.NET Core 的"请求管道"——每个 HTTP 请求进来，依次经过一个个中间件，最后到达你的 Controller。你的代码执行完，响应再原路返回。

形象理解：像流水线上的工作站。请求是工件，依次经过：

请求 → ExceptionHandler → Authentication → Authorization → Logging → Controller ← ← ← ← ← ←

典型的 Program.cs 中间件配置：

var app = builder.Build();

app.UseExceptionHandler();      // 全局异常处理（最外层）
app.UseAuthentication();        // 认证（你是谁？）
app.UseAuthorization();         // 授权（你能干什么？）
app.MapControllers();           // 路由到 Controller

app.Run();
面试重点："中间件的顺序很重要"——异常处理必须在最外面，才能捕获所有下游的异常。认证在授权之前，因为先知道你是谁才能判断你能做什么。

WCS 系统通常需要用户认证（操作员/工程师/管理员），JWT 是最常见的方式。

1.7 BackgroundService（后台长任务）

这个你特别占优——它本质上就是你的 PollingScheduler。

public class PlcPollingService : BackgroundService
{
    private readonly IPlcService _plc;

    public PlcPollingService(IPlcService plc)
    {
        _plc = plc;  // DI 注入
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await _plc.PollAllAsync(stoppingToken);
            }
            catch (Exception ex)
            {
                // 不能让后台任务静默死亡！！！
                Console.WriteLine($"轮询异常: {ex.Message}");
            }

            await Task.Delay(200, stoppingToken);  // 200ms 轮询间隔
        }
    }
}

在 Program.cs 中注册：

builder.Services.AddHostedService<PlcPollingService>();
面试话术："我深入了解 BackgroundService 模式，因为我的 WPF 项目里的 PollingScheduler 本质上就是同样的架构——一个后台长期运行的异步循环，用 CancellationToken 控制生命周期，用 SemaphoreSlim 控制并发。"

1.9 WCS 场景的典型 API 设计

面试官可能会问"你设计 WCS 的 API 会怎么写"，下面是一个参考：

[ApiController]
[Route("api/wcs")]
public class WcsController : ControllerBase
{
    // POST /api/wcs/tasks — WMS 下发任务
    [HttpPost("tasks")]
    public async Task<IActionResult> ReceiveTask(
        [FromBody] WmsTaskDto task)
    {
        await _service.EnqueueTaskAsync(task);
        return Accepted();  // 202 — 已接受，异步处理
    }

    // GET /api/wcs/devices — 获取所有设备状态
    [HttpGet("devices")]
    public IActionResult GetDeviceStatus()
    {
        var status = _service.GetAllDeviceStatus();
        return Ok(status);
    }

    // POST /api/wcs/devices/{id}/command — 手动控制设备
    [HttpPost("devices/{id}/command")]
    public async Task<IActionResult> SendCommand(
        int id, [FromBody] DeviceCommandDto cmd)
    {
        var result = await _service.ExecuteCommandAsync(id, cmd);
        if (result.Success) return Ok(result);
        return StatusCode(500, result);
    }
}
第二章

C# Task / async 精讲

JD 第一条"精通 Task 类的使用"，这是面试必考。你的项目里已经在用 Task 了，现在要能把原理讲清楚。

2.1 Task 是什么？为什么需要它？

工业场景里，你不能让 UI 卡住等 PLC 响应。读 DB 块可能要 50ms，如果 UI 线程等 50ms，用户就感觉卡了。Task 让你"等等，我不等"——发起读 DB 的操作后，UI 线程立刻回去处理界面的刷新和鼠标点击，等数据回来了自动回到代码里继续执行。

// 错误做法：阻塞 UI 线程
var data = _plc.ReadDbBlock(1, 0, 10);  // UI 卡死 50ms
TextBlock.Text = data.ToString();

// 正确做法：异步
var data = await _plc.ReadDbBlockAsync(1, 0, 10);  // UI 不卡
TextBlock.Text = data.ToString();

2.2 async/await 的底层原理（面试高频）

很多人背"状态机"，但理解这个就够了：

public async Task<int> GetPlcDataAsync()
{
    Console.WriteLine("1. 开始");  // 同步执行

    int result = await ReadFromPlcAsync();  // ★ 遇到 await，返回

    Console.WriteLine("3. 结束");  // ★ 数据回来了，继续执行
    return result;
}

执行流程（面试时这样说）：

1. 调用 GetPlcDataAsync() 时，先同步执行到 await 2. 遇到 await，检查 ReadFromPlcAsync() 是否已完成 3. 如果没完成，方法"暂停"，立即返回一个 Task<int> 给调用方 4. 调用方可以做别的事，不阻塞 5. 等 ReadFromPlcAsync() 返回数据，方法"恢复"，继续执行后面的代码 6. 返回结果 关键：await 不是"等待完成"，而是"还没完成就返回，完成了再回来"。
面试话术："async 方法遇到 await 时，如果操作没完成，会捕获当前上下文（SynchronizationContext），返回未完成的 Task，然后在操作完成时通过回调恢复到原来的上下文继续执行。编译器把 async 方法转成一个状态机结构。"

2.3 Task.Run 和 await 的区别

很多人搞混这两个概念，面试经常被问：

// 情况 1：Task.Run — 把同步代码放到线程池跑（CPU 密集型）
int result = await Task.Run(() => HeavyCalculation());

// 情况 2：直接 await — 异步方法本来就是异步的（IO 密集型）
byte[] data = await _plc.ReadAsync();  // 正确，这已经是 IO 异步

// 错误：把本来就是异步的方法包装到 Task.Run 里
byte[] data = await Task.Run(() => _plc.ReadAsync());
// ↑ 多此一举，浪费一个线程池线程

2.4 ConfigureAwait(false)

面试高频考点，一句话说清楚：

// 默认：await 会尝试"回到原来的上下文"（比如回到 UI 线程）
await ReadFromPlcAsync();
UpdateUI();  // 这行在 UI 线程上执行（因为默认回到了 UI 上下文）

// ConfigureAwait(false)：不回到原来的上下文
await ReadFromPlcAsync().ConfigureAwait(false);
UpdateUI();  // ★ 不一定在 UI 线程！如果在后台服务层，没问题
            //   如果在 UI 层用，操作 UI 控件会崩溃！
面试话术："在服务层（类库、BackgroundService）用 ConfigureAwait(false) 避免不必要的上下文切换，提升性能。在 UI 层不用，因为后面的代码需要回到 UI 线程操作控件。简单说——库代码用 false，应用代码不用管。"

2.5 Task.WhenAll / WhenAny

WCS 里很实用：同时读多个 DB 块，或同时监控多台设备。

// WhenAll — 等所有任务完成（并行执行）
var task1 = _plc1.ReadDbAsync(1, 0, 10);
var task2 = _plc2.ReadDbAsync(2, 0, 10);
var task3 = _plc3.ReadDbAsync(3, 0, 10);

await Task.WhenAll(task1, task2, task3);
// 此处三个结果都拿到了，总耗时 = 最慢的那个，不是三个之和

// WhenAny — 哪个先完成就用哪个（用于超时场景）
var completed = await Task.WhenAny(
    ReadFromPlcAsync(),
    Task.Delay(5000)  // 5 秒超时
);
if (completed == delayTask)
{
    Console.WriteLine("超时！");
}

2.6 CancellationToken — 正确停止后台任务

你的 PollingScheduler 里用了，但面试官可能深问。

public class PollingScheduler
{
    private CancellationTokenSource _cts;
    private Task _pollingTask;

    public void Start()
    {
        _cts = new CancellationTokenSource();
        _pollingTask = RunPollingLoopAsync(_cts.Token);
    }

    public async Task StopAsync()
    {
        _cts?.Cancel();                    // 发信号
        try
        {
            await _pollingTask;           // 等循环优雅退出
        }
        catch (OperationCanceledException)
        {
            // 这是预期的——Token 被取消了
        }
        _cts?.Dispose();
    }

    private async Task RunPollingLoopAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)  // 检查是否要停止
        {
            try
            {
                await PollOnceAsync(ct);
                await Task.Delay(200, ct);  // ct 传进去，取消时 Delay 会立刻结束
            }
            catch (OperationCanceledException)
            {
                break;  // 被取消了，退出循环
            }
            catch (Exception ex)
            {
                // 记录异常，继续跑——不能让后台任务静默死亡
                Console.WriteLine($"轮询异常: {ex.Message}");
            }
        }
    }
}
面试对口：这就是你 PollingScheduler 的机制。面试官问"怎么停止后台轮询？"——"用 CancellationTokenSource 发信号，循环体检测 IsCancellationRequested，Task.Delay 也传入 Token 实现快速响应。"

2.7 SemaphoreSlim — 控制并发

你的 S7Service 里多线程读写同一个 PLC 连接时需要串行化。

public class S7Service
{
    private readonly SemaphoreSlim _lock = new(1, 1);
    // 参数：(initialCount: 1, maxCount: 1) — 一次只允许 1 个进入

    public async Task<byte[]> ReadAsync(int db, int start, int size)
    {
        await _lock.WaitAsync();  // 排队等待（异步不阻塞线程）
        try
        {
            return await _client.ReadAreaAsync(db, start, size);
        }
        finally
        {
            _lock.Release();  // 释放锁，下一个排队者进入
        }
    }
}
面试话术："PLC 连接不是线程安全的，多线程并发读写会导致数据错乱。我用 SemaphoreSlim 控制同一时间只有一个操作在执行。和 lock 比，SemaphoreSlim 支持异步等待（await），lock 不支持。"

2.8 Task 异常处理（常犯的错误）

后台任务最容易犯的错误：异常没被捕获，任务静默消失。

// ❌ 错误：异常被吞了，任务静默死亡
_ = Task.Run(() => ThrowException());

// ✅ 正确：捕获异常
_ = Task.Run(() =>
{
    try { ThrowException(); }
    catch (Exception ex) { LogError(ex); }
});

// ❌ 错误：async void — 异常无法被捕获，会直接崩溃进程
async void Button_Click() { await DoSomething(); }

// ✅ 正确：async Task
private async Task Button_Click() { await DoSomething(); }
第三章

WCS 业务逻辑

即使技术再强，不懂 WCS 的业务流程也会让面试官觉得"这个人没有行业理解"。这一章让你快速掌握 WCS 的核心逻辑。

3.1 WCS 在整个系统中的位置

┌─────────────────────────────────────────┐ │ ERP / MES — 企业管理系统 │ │ 下订单、排产计划 │ └────────────────┬────────────────────────┘ │ HTTP / WebService / 中间表 ┌────────────────▼────────────────────────┐ │ WMS — 仓储管理系统（管库存、管账目） │ │ "把托盘 A 从入库口存到 B01-03 货位" │ └────────────────┬────────────────────────┘ │ REST API / 消息队列 ┌────────────────▼────────────────────────┐ │ ★ WCS — 仓库控制系统（你的岗位） │ │ "拆任务、调设备、追状态" │ └──────────┬─────┬──────────┬────────────┘ │ │ │ ┌──────┘ │ ┌─────┘ ▼ ▼ ▼ 堆垛机 AGV 输送线 ← 各设备有自己的 PLC 提升机 分拣机

关键：WMS 说"要做什么"，WCS 说"怎么做"，PLC 负责"动手做"。

3.2 一个完整的"入库任务"流程

Step 1：WMS 下发任务
POST /api/wcs/tasks
{
  "taskId": "IN-20260708-001",
  "type": "入库",
  "palletId": "P20260708001",
  "source": "入库口1",       // 从哪里取货
  "target": "A01-03-05"     // 放到哪里
}
Step 2：WCS 收到任务后

WCS 不会直接把任务发给堆垛机，而是拆解成子任务：

子任务 1: AGV-003 → 去入库口1，取托盘 P20260708001
子任务 2: AGV-003 → 运到站台 Z-102
子任务 3: 堆垛机-01 → 从站台 Z-102 取货
子任务 4: 堆垛机-01 → 移动到 A01-03-05（X/Y/Z 坐标）
子任务 5: 堆垛机-01 → 把货存入货位
Step 3：资源调度

WCS 要做三件事：

  • 选谁干：哪台 AGV 最近？哪个堆垛机空闲？
  • 预约资源：站台 Z-102 现在空着吗？预约锁定
  • 下发指令：通过 S7 协议写堆垛机 PLC 的数据块
Step 4：执行和追踪

从堆垛机 PLC 读状态字，判断执行进度。状态字可能的设计：

DB1.DBW0  — 状态字
  Bit 0: 空闲
  Bit 1: 运行中
  Bit 2: 到达目标
  Bit 3: 取货完成
  Bit 4: 放货完成
  Bit 5: 故障
  Bit 6: 急停

DB1.DBD2  — 目标货位 X 坐标
DB1.DBD6  — 目标货位 Y 坐标
DB1.DBD10 — 目标货位 Z 坐标
DB1.DBW14 — 任务号（WCS 分配）
面试中这样说："WCS 通过 S7 协议写堆垛机的 DB 块下发指令（目标坐标+任务号），然后通过轮询读状态字判断执行进度。每个子任务完成后，WCS 把状态汇总回传给 WMS。"

3.3 核心难点 1：任务调度策略

如果有 5 个出库任务同时进来，怎么分给 2 台堆垛机？

public class TaskScheduler
{
    private readonly PriorityQueue<WcsTask, int> _queue = new();

    public void Enqueue(WcsTask task)
    {
        int priority = task.TaskType switch
        {
            "紧急出库" => 1,  // 最小数字 = 最高优先级
            "出库"     => 2,
            "入库"     => 3,
            "移库"     => 4,
            _           => 5,
        };
        _queue.Enqueue(task, priority);
    }

    public WcsTask? Assign(StackerDevice stacker)
    {
        if (_queue.Count == 0 || !stacker.IsIdle) return null;
        var task = _queue.Dequeue();
        task.AssignedDevice = stacker.Id;
        return task;
    }
}

3.4 核心难点 2：死锁

场景：站台 A 被堆垛机 1 预约了，堆垛机 1 在等站台 A 空出来，但站台 A 上的货需要堆垛机 1 来取——死锁了。

常见解法（面试说出来就很加分）：

  • 预约机制：分配任务前先检查资源是否可用，不可用就不分配
  • 超时释放：任务预定资源后没有执行，超时自动释放
  • 戒环检测：A 等 B，B 等 A → 发现环后强制取消其中一个
面试话术："死锁是 WCS 最容易被忽略的问题。我设计时采用预约+超时双重机制——分配任务前先锁定路径资源，锁定失败就排队等待，超过 30 秒锁定未释放则触发告警人工介入。"

3.5 核心难点 3：断点续传

任务执行到一半，堆垛机故障了怎么办？

  • WCS 记录每个子任务的当前状态（未开始/执行中/已完成/故障中断）
  • 故障恢复后，WCS 从 DB 中查旧任务状态，从中断的地方继续
  • 如果无法继续（货还在半路），走人工确认流程
第四章

S7 协议深度

这是你的强项，但面试时要比别人讲得更深。不光说"我用 Sharp7 读 DB 块"，而要讲清楚协议层级、技术选型理由。

4.1 S7 协议三层结构

┌─────────────────────────────────────┐ │ S7 Communication Layer │ │ (Job Request / Ack Data) │ │ 功能码：0x04 (Read), 0x05 (Write) │ ├─────────────────────────────────────┤ │ ISO-COTP Layer (Transport) │ │ TPKT (4 bytes) + COTP (3+ bytes) │ │ CR/CC/DT — 连接建立和数据传输 │ ├─────────────────────────────────────┤ │ TCP Layer │ │ Port 102, 三次握手 │ └─────────────────────────────────────┘

三层通俗理解：

  • TCP：快递把包裹从北京送到上海
  • ISO-COTP：收货时确认"是给我的"，发起连接"CR"和确认"CC"
  • S7：包裹里面的具体物品——"我要读 DB1 从第0个字节开始的10个字节"

4.2 Sharp7 核心操作（你项目里就在用）

// 1. 创建客户端并连接
var client = new S7Client();
int result = client.ConnectTo("192.168.0.1", 0, 1);
// 参数: IP, Rack(0), Slot(1) — 1200/1500 通常用 0/1

if (result == 0)  // 0 = 成功
{
    Console.WriteLine("连接成功！");
}

// 2. 读 DB 块
byte[] buffer = new byte[10];
result = client.ReadArea(S7Consts.S7AreaDB,  // 区域：DB 块
    1,                    // DB 编号
    0,                    // 起始偏移（字节）
    10,                   // 读取长度（字节）
    buffer);

// 3. 写 DB 块
byte[] data = { 0x01, 0x02, 0x03 };
result = client.WriteArea(S7Consts.S7AreaDB, 1, 0, data.Length, data);

4.3 S7 地址区域对照表

S7AreaPE  = 0x81  — 输入 (I)     — 从 PLC 读传感器信号
S7AreaPA  = 0x82  — 输出 (Q)     — 控制继电器/指示灯
S7AreaMK  = 0x83  — 位存储 (M)   — 中间变量
S7AreaDB  = 0x84  — 数据块 (DB)  — ★ 最常用，读写数据
S7AreaCT  = 0x1C  — 计数器 (C)
S7AreaTM  = 0x1D  — 定时器 (T)

4.4 BOOL 打包与解析（你的项目刚改过的）

面试官超级喜欢问这个问题："你从 PLC 读回来的 BOOL 怎么解析？"

// PLC 中 BOOL 的存储规则：
// 1. 8 个 BOOL 打包成 1 个 BYTE
// 2. 起始地址必须是 BYTE 边界（不能从第 3 位开始）
// 3. Bit 0 = 最低位

// 从 DB1.DBX0.0 到 DB1.DBX0.7 共 8 个 BOOL
// 读回来的 buffer[0] 包含 8 个 BOOL

byte[] buffer = new byte[1];
client.ReadArea(S7Consts.S7AreaDB, 1, 0, 1, buffer);

bool bit0 = (buffer[0] & 0x01) != 0;  // DBX0.0
bool bit1 = (buffer[0] & 0x02) != 0;  // DBX0.1
bool bit2 = (buffer[0] & 0x04) != 0;  // DBX0.2
bool bit3 = (buffer[0] & 0x08) != 0;  // DBX0.3
bool bit4 = (buffer[0] & 0x10) != 0;  // DBX0.4
bool bit5 = (buffer[0] & 0x20) != 0;  // DBX0.5
bool bit6 = (buffer[0] & 0x40) != 0;  // DBX0.6
bool bit7 = (buffer[0] & 0x80) != 0;  // DBX0.7
面试高频追问："一个 DB 块里 BOOL 和 WORD 混排，怎么计算偏移？"
回答：在博途中，BOOL 会按 WORD 边界对齐。如果你的变量声明是：BOOL（占用 1 位但占 2 字节偏移）、INT（2 字节）、下一个 BOOL 从第 4 字节开始。不能简单地"上一个结束就是下一个开始"。

4.5 重连策略（指数退避）

private async Task EnsureConnectedAsync(CancellationToken ct)
{
    int retryDelay = 1000;  // 初始 1 秒
    const int maxDelay = 30000;  // 最大 30 秒

    while (!ct.IsCancellationRequested)
    {
        if (_client.Connected) return;

        var result = _client.ConnectTo(_ip, _rack, _slot);
        if (result == 0)
        {
            Console.WriteLine("重连成功");
            return;
        }

        Console.WriteLine($"重连失败，等待 {retryDelay}ms...");
        await Task.Delay(retryDelay, ct);

        // 指数退避：1s → 2s → 4s → 8s → 16s → 30s
        retryDelay = Math.Min(retryDelay * 2, maxDelay);
    }
}
面试话术："PLC 断联是工业现场的常态——网线松动、PLC 重启、交换机掉电。指数退避可以避免 PLC 刚恢复时被大量重连请求冲垮。这是 TCP 拥塞控制的思路在应用层的平移。"

4.6 多 DB 块的分时轮询策略

你的 PollingScheduler 的思路，面试时要用能说清楚的话表达：

// 如果有 5 个 DB 块要读，不要在一个循环里全读：
// ❌ 错误：一个循环里串行读 5 个 DB（太慢）
foreach (var db in dbList) { await ReadDbAsync(db); }

// ✅ 正确：分时轮转
// 每轮只读 1-2 个 DB，下一轮读另外的，
// 这样单个请求的响应时间就均匀了

private int _currentIndex = 0;

private async Task PollOnceAsync()
{
    var db = _dbList[_currentIndex];
    await ReadDbAsync(db);
    _currentIndex = (_currentIndex + 1) % _dbList.Count;
}

面试回答模板

下面是一些你可能直接套用的表述，面试时用这些说法会显得专业。

Q：你为什么从 Web 前端转 WCS / 上位机？

"我有 5 年+ 编程经验，前端和后端都做过，完整项目全栈开发能力。接触工业控制后发现，代码最终能控制真实的物理设备——堆垛机、输送线在动，这比纯软件更有成就感。我的电气化系统实训让我理解了工业现场的工作流程，前端背景让我做的界面天然好用。而且 WCS 这个方向，我的编程能力和通讯协议经验能直接复用，学习曲线不陡。"

Q：描述一下你的 PollingScheduler 设计

"我的 PollingScheduler 采用双通道架构。快通道处理 I/Q/M 区域，要求 200ms 刷新率；慢通道处理 DB 块，数据量大但不需要那么快。两个通道用独立的 S7 连接，互不干扰——这样慢的 DB 读取不会阻塞实时的 I/Q/M 刷新。每个通道内部用 SemaphoreSlim 控制并发，请求串行化防止冲突。通道有一个 CancellationToken 控制生命周期，在应用关闭时能优雅停止。"

Q：多线程读 PLC，怎么保证数据不错？

"Sharp7 的客户端不是线程安全的。我用了两种机制：（1）SemaphoreSlim(1,1) 做请求排队，同一时刻只有一个读写操作在执行；（2）对于不同刷新率的需求，用独立连接——快通道一个连接，DB 通道另一个连接，这样高频率和低频次的请求不会相互干扰。"

Q：如果 PLC 断了，你的程序怎么办？

"三步策略：（1）每次轮询前检查连接状态（Connected 属性），断开就走重连流程；（2）指数退避重连——1s、2s、4s、8s 递增，最大 30s，防止 PLC 刚恢复时被冲垮；（3）连接恢复后自动继续轮询，不需要人工干预。如果长时断联，UI 上会显示红色断开状态条。"

Q：WMS 和 WCS 有什么区别？

"WMS 管库存、管账目、管业务——它知道仓库里有什么东西，知道应该放到哪个货位。WCS 管设备、管调度、管执行——它把 WMS 的任务拆成具体的设备动作指令。举例子：WMS 说'托盘 A 入库到 B01-03'，WCS 就负责安排谁去取、谁运输、谁上架，通过 S7 协议下发给 PLC 执行。WMS 是仓库的大脑，WCS 是神经中枢，PLC 是肌肉。"
