第一章

前端视角看后端——请求全程图解

你在前端每天做的事：

fetch('http://localhost:5000/api/tasks', {
  method: 'GET',
  headers: { 'Authorization': `Bearer ${token}` },
})
  .then(res => res.json())
  .then(data => console.log(data))

这个 fetch 请求到 ASP.NET Core 后端之后，发生了什么：

你的 Vue 页面 ASP.NET Core 服务器 ┌──────────────┐ fetch('/api/tasks') ───────→│ Middleware │ ← 像 Express 的 app.use() Authorization: Bearer xxx │ ① 认证中间件 │ 一个个"关卡"过 │ ② 路由匹配 │ └──────┬───────┘ ▼ ┌──────────────┐ │ Controller │ ← 类似 React 的"页面组件" │ TaskController│ 负责一个功能模块的所有接口 │ │ │ [HttpGet] │ │ GetTasks() │ └──────┬───────┘ ▼ ┌──────────────┐ │ Service │ ← 和你 WPF 项目里的 Service 一样 │ TaskService │ 你的 S7Service 直接搬过来用 │ │ │ .ReadDb() │ → 读 PLC 或查数据库 └──────┬───────┘ ▼ ┌──────────────┐ ←────── JSON 响应 ───────│ return Ok() │ ← 像 res.json() { tasks: [...] } └──────────────┘

一句话：你的 fetch 发请求 → Controller 接 → Service 干活 → Controller 返回 JSON → 你的 .then() 收到数据。和你前端调 Node.js 后端的流程一模一样。

第二章

最快的上手路径——从 dotnet new 开始

别从头搭项目，直接用模板。面试官问"你建过 ASP.NET Core 项目吗"，你说"脚手架一键生成"，谁都用过。

# 终端执行（你已经装了 dotnet 10）
dotnet new webapi -n MyWcsApi
cd MyWcsApi
code .
dotnet run

这四条命令就起了一个可用的 WebAPI 服务器，默认端口 5000/5001。

生成的目录结构和前端对比：

你的前端项目
src/
├── components/
│ └── TaskBoard.tsx
├── services/
│ └── api.ts
├── App.tsx
└── vite.config.ts
ASP.NET Core WebAPI 项目
Controllers/
│ └── TaskController.cs
Services/
│ └── TaskService.cs
Program.cs
appsettings.json
对应关系：Program.cs 相当于 vite.config.ts（启动配置），Controllers/ 是"路由层"（类似 Next.js 的 pages/），Services/ 就是你的业务逻辑（和你 WPF 项目里的 Services/ 一样）。
第三章

核心语法——Controller（你只需会写这个）

Controller 就是后端的"组件"。一个 Controller 管一类资源（比如任务相关的所有 API）。

最简例子：
using Microsoft.AspNetCore.Mvc;
using MyWcsApi.Models;

// 这个类和它的属性标注，就决定了路由
[ApiController]                          // 告诉框架"这是个 API 控制器"
[Route("api/[controller]")]            // [controller] 自动替换为类名(去Controller)
public class TaskController : ControllerBase // 继承 ControllerBase
{
    /// GET /api/tasks  ← 对应前端的 fetch('/api/tasks')
    [HttpGet]
    public IActionResult GetTasks()
    {
        return Ok(new[] { "任务1", "任务2" });
        // OK() ≈ res.json() — 返回 200 + JSON
    }

    /// GET /api/tasks/5  ← 路由参数 {id}
    [HttpGet("{id}")]
    public IActionResult GetTask(int id)  // id 自动从 URL 里的 {id} 拿到
    {
        return Ok($"任务 {id}");
    }

    /// POST /api/tasks  ← 前端发 POST 请求
    [HttpPost]
    public IActionResult CreateTask([FromBody] TaskDto dto)
    {
        // [FromBody] = 从请求 body 的 JSON 里反序列化
        // 前端发：fetch(url, { method:'POST', body: JSON.stringify({...}) })
        // 后端自动把 JSON 转成 TaskDto 对象
        return Created($"/api/tasks/{dto.Id}", dto);
        // Created() ≈ 201 状态码 + 新资源位置
    }
}
你只需要记住：每个方法上面贴一个标签 [HttpGet] / [HttpPost] / [HttpPut] / [HttpDelete]，加上路径，就是前端调的那个 API 端点。返回值用 Ok() / Created() / NotFound() 代替 res.json() / res.status()。
对比你可能的 Express 写法：
你大概知道的 Express
app.get('/api/tasks', (req, res) => {
  res.json([...])
})

app.post('/api/tasks', (req, res) => {
  const body = req.body
  res.status(201).json(body)
})
ASP.NET Core
[HttpGet]
public IActionResult Get()
{ return Ok([...]); }

[HttpPost]
public IActionResult Create(
  [FromBody] TaskDto dto
)
{ return Created(...); }
DTO —— 后端的 TypeScript interface

你在前端写 TypeScript 定义接口：

// 前端 TypeScript
interface TaskDto {
  id: number;
  taskType: string;  // '入库' | '出库'
  source: string;
  target: string;
}

C# 里写几乎一样的东西：

// 后端 C#
public class TaskDto
{
    public int Id { get; set; }
    public string TaskType { get; set; } = "";
    public string Source { get; set; } = "";
    public string Target { get; set; } = "";
}

区别只有：C# 用 { get; set; } 代替 TypeScript 的 field: type。然后 [FromBody] 把前端 POST 来的 JSON 自动转成这个对象——你不需要 JSON.parse()。

第四章

你的 WPF Service 层在后端怎么用

你在 WPF 项目里已经写好了 S7Service、PollingScheduler、AlarmService，它们都是纯 C#，没有 UI 依赖。

好消息：这些类可以直接搬到 ASP.NET Core 项目里用。

在你的 WPF 项目里注册服务：

// App.xaml.cs（WPF）
services.AddSingleton<S7Service>();
services.AddSingleton<PollingScheduler>();

在 ASP.NET Core 项目里注册服务：

// Program.cs（ASP.NET Core）—— 写法一样
builder.Services.AddSingleton<S7Service>();
builder.Services.AddSingleton<PollingScheduler>();
builder.Services.AddHostedService<PollingScheduler>(); // 让后台轮询自动跑

在你的 Controller 里用这些服务：

[ApiController]
[Route("api/plc")]
public class PlcController : ControllerBase
{
    private readonly S7Service _s7;

    // 构造函数注入——就像 Vue 的 inject/provide 或 React Context
    public PlcController(S7Service s7)
    {
        _s7 = s7;
    }

    [HttpGet("db/{dbNumber}")]
    public async Task<IActionResult> ReadDb(int dbNumber)
    {
        var data = await _s7.ReadDbAsync(dbNumber, 0, 10);
        return Ok(data);
    }
}
核心理解：你的 Service 层（S7Service、AlarmService 等）在 WPF 和 ASP.NET Core 之间是完全可复用的。差别只在"入口"不同——WPF 入口是界面按钮点击，WebAPI 入口是 HTTP 请求。面试时说出这一点非常加分。
第五章

Program.cs —— 像 vite.config.ts 一样的东西

Program.cs 是整个后端的入口配置文件。类比前端的配置文件：

前端 vite.config.ts: 后端 Program.cs: defineConfig({ var builder = WebApplication.CreateBuilder(args); plugins: [vue()] builder.Services.AddControllers(); server: { port: 5173 } builder.Services.AddSingleton(); }) builder.Services.AddAuthentication()... builder.Services.AddSwaggerGen() var app = builder.Build(); app.UseAuthentication() app.MapControllers() app.Run()

一个 WCS 项目典型的 Program.cs 长这样：

var builder = WebApplication.CreateBuilder(args);

// ── 1. 注册服务（≈ 前端的 provide/inject） ──
builder.Services.AddControllers();
builder.Services.AddSingleton<S7Service>();        // 你的 PLC 服务
builder.Services.AddSingleton<WcsTaskService>();   // WCS 任务处理
builder.Services.AddHostedService<PlcPollingService>(); // 后台轮询

// ── 2. 配置 JWT 认证 ──
builder.Services.AddAuthentication().AddJwtBearer(/*...*/);

// ── 3. 构建 app ──
var app = builder.Build();

// ── 4. 中间件管道（≈ 前端的拦截器/守卫） ──
app.UseAuthentication();        // 先认证（你是谁？）
app.UseAuthorization();         // 再授权（你能干啥？）
app.MapControllers();           // 最后路由到 Controller

app.Run();
面试话术："Program.cs 是 ASP.NET Core 的入口，相当于前端的 vite.config.ts + router 配置。在这里注册服务、配置中间件、定义管道顺序。"
第六章

面试够用的 JWT 认证

你在前端肯定调过带 token 的 API：fetch(url, { headers: { Authorization: 'Bearer xxx' } })。后端这边就是生成这个 token 和验证它。

生成 Token（登录接口）：
[HttpPost("login")]
public IActionResult Login([FromBody] LoginDto dto)
{
    // 校验用户名密码（省了）

    // 生成 token
    var key = new SymmetricSecurityKey(
        Encoding.UTF8.GetBytes("你的密钥至少16个字符"));
    var token = new JwtSecurityToken(
        issuer: "MyWcsApi",
        audience: "MyWcsClient",
        claims: new[] { new Claim(ClaimTypes.Role, dto.Role) },
        expires: DateTime.Now.AddHours(8),
        signingCredentials: new SigningCredentials(key, SecurityAlgorithms.HmacSha256)
    );

    return Ok(new { token = new JwtSecurityTokenHandler().WriteToken(token) });
}
保护接口（加一个标签就行）：
[ApiController]
[Route("api/tasks")]
[Authorize(Roles = "工程师")]  // ← 只加这一行，没有 token 或角色不对就 401
public class TaskController : ControllerBase
{ ... }
面试够用程度：面试不会让你手写 JWT 实现，他知道你用过就会。你只需要说出"前端发请求带 Bearer Token，后端用 [Authorize] 标签保护接口，Program.cs 里配置 JWT 验证参数"就足够了。
第七章

WCS 场景的完整 API 示例

这是面试官最想听到的东西——你能把后端技术和 WCS 业务结合起来说，而不是背语法。

一个 WCS 后端典型要做的事：

  • 从 WMS 接收任务（入库/出库/移库指令）
  • 查询所有设备状态（堆垛机/AGV/输送线）
  • 下发控制指令给 PLC
  • 向前端推送实时数据
[ApiController]
[Route("api/wcs")]
public class WcsController : ControllerBase
{
    private readonly WcsTaskService _taskSvc;

    public WcsController(WcsTaskService taskSvc)
    {
        _taskSvc = taskSvc;  // DI 注入，不要 new
    }

    // POST /api/wcs/tasks  -- WMS 下发任务
    [HttpPost("tasks")]
    public async Task<IActionResult> ReceiveTask([FromBody] WmsTaskDto task)
    {
        await _taskSvc.EnqueueAsync(task);  // 入队等待调度
        return Accepted();  // 202 表示"已接受，正在处理"
    }

    // GET /api/wcs/devices  -- 获取所有设备状态
    [HttpGet("devices")]
    public IActionResult GetDevices()
    {
        var status = _taskSvc.GetAllDeviceStatus();
        return Ok(status);
        // 返回的 JSON 长这样：
        // [{ "id": 1, "name": "堆垛机01", "status": "运行中", "position": { "x":10, "y":5 } }, ...]
    }

    // POST /api/wcs/devices/{id}/command  -- 手动控制设备
    [HttpPost("devices/{id}/command")]
    public async Task<IActionResult> SendCommand(
        int id, [FromBody] CommandDto cmd)
    {
        var result = await _taskSvc.ExecuteCommandAsync(id, cmd);
        if (result.Success) return Ok(result);
        return StatusCode(500, result);  // 执行失败
    }
}
面试话术："Controller 只负责接请求和返回响应，具体业务逻辑都在 Service 里。我把 S7Service、TaskScheduler 这些注入到 Controller 里用，和 WPF 项目里把 Service 注入到 ViewModel 里用是一样的模式。"
第八章

面试官问了怎么说

下面是几个面试里可能问到的问题，以及适合你（前端背景+WPF项目）的回答方式：

Q：你用过 ASP.NET Core 吗？

"我 WPF 项目的 Service 层就是纯 C#，理解 DI 和服务注入。ASP.NET Core WebAPI 的 Controller 对我来相当于前端 React 组件的逻辑层加路由，概念的对应的很清楚。虽然还没在实际项目里用过，但已经上手写过 demo，理解路由、Controller、Service 的分层、JWT 认证这些。后端对我来说就是'接 HTTP 请求 → 用我的 C# Service 处理 → 返回 JSON'。"

Q：你的 WPF 项目和 WebAPI 项目有什么区别？

"架构上最大的区别是前后端分离。WPF 里 ViewModel 既管数据又管界面状态，WebAPI 里 Controller 只管接口，前端（Vue/React）去管界面。但 Service 层是共通的——S7Service、AlarmService 这些在 WPF 里能用的，在 WebAPI 项目里直接搬过来用，只是入口从 WPF 按钮事件变成了 HTTP 请求。"

Q：你从没做过 WebAPI 项目，能胜任吗？

"我是前端出身，理解 HTTP 协议、RESTful API、JSON 序列化这些。ASP.NET Core 对我来说是'会用 C# 写后端接口'，而不是'学一个全新的后端范式'。我的 WPF Service 层可以直接复用，再加一层 Controller 处理 HTTP 请求就可以了。而且我 Vue 也熟，如果前端也是 Vue 做的，我能前后端都看得懂。"

启示：你不需要撒谎说"我做过很多 WebAPI 项目"，你需要让面试官确信"你有能力快速学会"。"前端+WPF C#" 的组合恰好说明你对"后端 API"和"C# 工业服务"两个方向都已经各自有基础了，就差把这两块连起来。
